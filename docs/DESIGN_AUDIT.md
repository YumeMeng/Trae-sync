# Trae Sync V1 设计审计

## 审计状态

- 审计对象：`docs/DESIGN_DISCUSSION.md` D-001 至 D-045
- 范围：功能正确性、数据完整性、恢复能力、产品语义和实现可验证性
- 不包含：安全漏洞审计
- 状态：A-001 至 A-019 均已形成产品决策或明确技术 Gate；Gate B 事实调查已通过

## P0：必须在实现前解决

### A-001：原始三件套备份不等于已证明可恢复的逻辑备份

状态：设计决策已由 D-023 解决；仍需 Gate C 实证。

当前方案要求复制 `database.db`、WAL、SHM。WAL 含可能尚未 checkpoint 的已提交页，SHM 是瞬态共享内存索引。虽然停机复制三件套保留了原始证据，但尚未证明在所有 WAL 状态下直接覆盖三件套都能稳定恢复。

建议采用双备份：

1. 原始证据快照：保留 DB/WAL/SHM 原字节和哈希。
2. 逻辑恢复副本：通过已打开的 SQLCipher 连接和 SQLite Backup API 生成单文件一致数据库，再独立打开并通过完整性检查。

恢复优先使用已验证逻辑副本；原始三件套用于审计、重新研究和最后手段。必须做包含未 checkpoint WAL 的恢复演练。

### A-002：目标数据库与工具目录库不存在跨库原子事务

状态：设计决策已由 D-024 解决；仍需 Gate C 的逐阶段崩溃注入实证。

同步同时改变目标 TRAE 数据库和工具自身目录库/操作日志。两者不能放在一个 SQLite 事务中。进程可能在“目标已提交、目录库未记成功”或“恢复已完成、目录库仍记失败”时崩溃。

需要持久化操作状态机：

```text
planned
backup_verified
target_writing
target_committed
target_verified
catalog_reconciled
completed
restore_required
restored
```

每个阶段保存目标指纹和备份 ID。应用启动时必须审计未完成操作，并根据目标指纹继续验证、完成目录协调或进入恢复流程，不能重新盲目执行计划。

### A-003：完整性检查失败后直接自动恢复仍有二次数据丢失风险

状态：设计决策已由 D-025 解决；仍需 Gate C 的失败分类、失败后取证、staging 恢复和替换中崩溃实证。

完整检查失败可能来自真实损坏，也可能来自临时 I/O、锁或读取错误。自动覆盖目标前必须先保存“失败后的目标状态”并验证写前恢复副本。否则自动恢复可能丢失用于诊断的数据，或用一个尚未证明可恢复的备份覆盖当前状态。

建议顺序：

```text
冻结目标
保存失败后证据快照
验证写前逻辑恢复副本
在 staging 路径完成恢复
验证 staging
替换目标
重开验证
保留失败后快照和操作日志
```

### A-004：当前账号检测真实格式验证

状态：Gate B 事实调查已通过；D-044 已禁止手工账号选择解锁写入，生产解析器和异常 fixture 留到实现 Gate。

实际 `storage.json` 的认证值是 Base64 包装的 `tc` 二进制密文，不是参考账号管理器代码假设的明文嵌套 JSON，也不能直接作为原始 DPAPI 数据解密。V1 不依赖私有 Electron ABI 解密认证正文。

产品代码和 10 个真实启动会话已确认 `alog.log fetchLogTask.userId`、`renderer.log RouteService User info loaded.userId` 和 `main.log updateUserInfo/getUserInfo.userId` 的当前账号语义。每个会话至少两类来源一致，覆盖 `2578820706078841` 与 `1804778984702451` 多次切换。`2490859781907946` 是设备 ID。

Adapter 使用权威日志账号、认证字段不可逆指纹和 Local Storage 当前账号作用域建立证据绑定。检测失败时不能根据已被同步修改过的 `project.user_id`、历史 `state.vscdb` 账号键或第三方账号管理器状态猜测。手工选择只能整理历史，不能授权写入。详细证据见 `docs/ACCOUNT_DETECTION_FEASIBILITY.md`。

## P1：会导致错误行为或产品语义混乱

### A-005：多次迁移后“来源账号”会被活动库当前归属覆盖

状态：设计决策已由 D-026 解决；仍需 Gate E 的账号间往返迁移和重复扫描实证。

扫描后 `project.user_id` 会随着每次同步改变。如果目录库只保存最新值，按来源账号筛选会逐渐把所有项目显示成最近目标账号。

目录模型至少需要区分：

```text
first_observed_owner
owner_observations[]
current_live_owner
user_assigned_source_label
```

来源筛选应使用稳定来源语义，而不是直接使用最新 `project.user_id`。

### A-006：只检查唯一索引不足以覆盖同路径项目冲突

状态：设计决策已由 D-027/D-038 解决；可靠同一项目生成会话并入计划，身份不明项目排除，仍需 Gate F 的真实 schema fixture 和 Work CN UI 行为实证。

已验证唯一冲突是 `(biz_project_id, user_id)`，但两个不同 `biz_project_id` 可能指向同一工作目录。转移后，目标账号可能出现同路径的多个项目记录；TRAE 如何选择或展示尚未验证。

预检还应比较规范化绝对路径、workspace 模式、transient fallback 和 remote project 标识。同路径冲突必须先在测试副本和 UI 中验证，不能自动迁移。

### A-007：会话版本“严格扩展”判定尚未定义规范化内容图

状态：设计决策已由 D-031 解决；仍需 Gate I 的真实重复扫描 fixture 和逐表语义映射实证。

TRAE 会更新 `updated_at`、摘要、压缩历史、删除标记和 FTS 数据。直接按行集合或整行哈希可能把正常维护误判为分叉，也可能忽略正文重写。

需要按表定义：稳定 ID、语义字段、易变字段、派生字段和有序关系。V1 写入不依赖该能力，但历史库版本展示和冲突预览依赖，必须通过真实重复扫描 fixture 验证。

### A-008：软删除“排除”与项目级归属迁移描述不精确

状态：设计决策与规格表述已由 D-032 解决；仍需 Gate J 的软删除关系和可见统计实证。

项目级 `user_id` 修改不会逐条排除软删除消息；这些行会随项目关系一起保留，只是 TRAE 正常查询通常不显示。规格应表述为“软删除内容不计入可见同步统计，也不恢复其可见状态”，而不是暗示物理上没有涉及这些行。

### A-009：平台选择不足以表达多个 Work CN 安装或 Profile

状态：设计决策已由 D-028 解决；仍需 Gate G 的多数据位置发现、身份绑定和误写防护实证。

用户可能存在默认目录、自定义 `--user-data-dir`、便携目录或多个 Profile。同步目标应是：

```text
(platform, installation/profile)
```

V1 至少需要自动检测一个默认 Profile、允许手动添加路径，并在所有快照、操作和备份记录中使用稳定 Profile ID。

## P2：不会阻断核心同步，但应在 V1 规格中明确

### A-010：DPAPI 丢失后目录库的人工决策和日志无法恢复

状态：设计决策已由 D-029 解决；仍需 Gate H 的 DPAPI 丢失、恢复包校验和新 Profile 重新包装实证。

原始快照仍可重建大部分对话，但 Windows Profile 损坏或迁移会使 DPAPI 保护的目录库 key 无法解锁，用户标签、版本选择和操作日志可能丢失。

V1 需要决定是否提供显式恢复密钥导出；若不提供，必须明确目录库可重建范围，并把关键操作清单额外保存为不含正文的可恢复记录。

### A-011：全库检查的耗时和进度需要真实基准

状态：产品与进度规则已由 D-033 解决；仍需 Gate K 的真实副本耗时、事件节流和 UI 响应性实证。

当前 Docker/Windows bind mount 的全库检查曾持续数分钟，而容器内部副本明显更快。嵌入式 SQLCipher 的真实耗时未知。Gate A/D 应记录 257 MB 实际副本的各阶段耗时，并确保 UI 阶段进度不是虚假百分比。

### A-012：磁盘空间预检必须覆盖峰值而非文件大小

状态：设计决策已由 D-034 解决；仍需 Gate L 的真实峰值、空间预留和跨卷迁移故障实证。

一次同步可能同时存在来源快照、逻辑备份、写前原始快照、失败后快照、staging 恢复副本和 WAL。只按数据库大小检查空间不足。

Sync Planner 应计算本次操作保守峰值空间；不足时在关闭 TRAE 和创建部分备份前停止。

## 第二轮一致性复审

### A-013：已验证的是归属转移，不是双账号同时保留副本

状态：产品决策已由 D-035 解决；V1 采用“历史跟随当前账号”，双账号同时保留不进入 V1。

D-004 把普通同步描述为“非破坏性并集”，容易被理解为源账号和目标账号同时拥有历史。但当前唯一实测操作是修改 `project.user_id`；原始执行手册和结构文档明确说明它不复制会话图，迁移后源账号不再拥有这些项目的当前可见归属，切回源账号时需要再次转移。

V1 必须在以下语义中明确选择：

```text
历史跟随当前账号：项目归属移动到当前账号；安全、已实测
双账号同时保留：深度克隆完整项目关系图；尚未实现或验证
```

V1 已明确采用“历史跟随当前账号”，把目标账号结果描述为并入，并如实显示来源账号将失去这些项目的当前可见归属。真正双账号独立副本留给完整 ID 克隆 Gate。

### A-014：项目级写入无法执行会话级冲突排除

状态：已由 D-037 解决。V1 支持活动数据库会话级重挂和单会话选择；真实 UI 继续对话仍需 Gate M。

原 D-003 和 D-017 曾把 V1 限定为只通过项目级 `project.user_id` 迁移，不提供单会话写入；但 D-006 和 D-015 又要求遇到分叉时只跳过受影响会话并继续同步其他内容。一次项目归属更新会让该项目的全部会话一起跟随，无法只排除其中一个会话。

新的结构证据表明，会话内容图绝大多数通过稳定 `session_id` 关联。保持所有内容 ID 不变，仅修改 `chat_session.project_id`、`session_project.project_id` 和按会话限定的项目引用，即可把一条完整会话挂到目标账号已有项目。

明文与 SQLCipher 加密副本均已完成“单条移动 -> 剩余会话合并 -> 反向挂回”验证，覆盖 7 条会话、68 条消息、3508 条 `history_v2` 和 8018 条 `server_history_info`。正文闭包哈希不变，项目唯一约束、FTS、关系一致性和两层完整性检查通过。

因此 A-014 不再是数据库粒度矛盾。剩余风险是目标 sandbox 项目配置、含 snapshot/artifact/worktree 的新型会话，以及重挂后继续发送消息的真实 UI 行为。旧归档版本写回仍是另一项能力，不能与活动会话重挂混用。

最终规格复核补充了能力边界：单会话重挂要求目标账号已经存在可靠匹配的逻辑项目。目标账号没有该项目时，现有 `FollowProject` 只能移动整个项目；若自定义范围只选了部分会话，Planner 必须排除并提示选择整个项目，不能静默扩大范围。自动创建目标项目行和 sandbox 配置未完成真实 UI 验证，不进入 V1。

### A-015：恢复状态和崩溃判定尚未形成一套可执行协议

状态：设计已由 D-039 解决；仍需 Gate C 对每个非终态进行崩溃注入和重启协调实证。

D-024 的状态列表与 D-025 的恢复状态不是同一套状态机，也缺少 `cancelled_before_write`、`not_applied`、`failed_safe` 等终态。更关键的是，SQLite 在崩溃恢复或 checkpoint 后可能产生不同 DB/WAL 字节布局，不能只用文件哈希判断目标处于写前还是写后逻辑状态。

D-039 已建立唯一状态与终态集合，并同时使用：

```text
物理证据：文件身份、存在性、大小和哈希
逻辑证据：计划涉及的项目归属、数量、schema 与关系断言
```

物理哈希用于证明备份和识别外部变化；崩溃后是否已提交以只读打开后的逻辑不变量协调，禁止盲目重放写事务。明确未提交时结束为 `not_applied`；明确已提交且验证通过时继续完成；明确异常且满足全部条件时受控自动恢复；任何未知状态进入 `manual_recovery_required` 并冻结写入。

### A-016：同步计划未绑定账号证据，也没有跨进程排他

状态：设计已由 D-040 解决；Gate B 真实账号证据调查已通过，仍需完成生产解析器，并由 Gate C/G 验证崩溃协调、双进程和账号管理器并发切换。

当前计划绑定目标数据库指纹，但账号管理器可能在 TRAE 已关闭时修改 `storage.json`，另一个 Trae Sync 进程也可能同时规划或写入。这样会出现预览显示账号 A、实际写入时当前登录已变成账号 B，或两个进程交错更新 manifest 和数据库。

计划至少必须绑定：

```text
data_location_id
current_user_id
账号证据指纹及读取时间
数据库物理与逻辑指纹
```

D-040 要求点击应用后获取目录库单写锁和数据位置跨进程排他锁，协调未完成 manifest，再重新读取并比较全部证据；提交前再次发现账号漂移则回滚，提交后才发现外部漂移则停止启动 TRAE 并进入协调，绝不静默改投。第二实例只能浏览已提交历史，不能对同一数据位置启动有副作用的操作。

### A-017：DB/WAL/SHM 的存在性和恢复规则不完整

状态：设计已由 D-041 解决；仍需 Gate C 覆盖文件存在性变化、未 checkpoint WAL、残留 WAL 和恢复中断。

正常关闭和 checkpoint 后，`database.db-wal` 或 `database.db-shm` 可以不存在。当前“备份三件套，任一失败则停止”的措辞没有区分“文件本来不存在”和“复制失败”，可能让正常数据库永远无法写入。另一方面，使用单文件逻辑副本恢复时若目标目录残留失败状态的 WAL，会重新应用错误页面。

D-041 要求 manifest 逐项记录存在或不存在；`database.db` 必须存在，WAL/SHM 仅在捕获状态存在时复制并验证。逻辑副本恢复时先保存并隔离目标 DB/WAL/SHM，再发布已验证单文件数据库；旧 WAL/SHM 不复用、不直接删除，由 SQLite 在验证连接中按需重新创建。

### A-018：Trae Sync 自身目录库升级缺少数据迁移保护

状态：当前基线已由 D-042 解决；具体迁移链和兼容范围随真实版本更新重新评审，并需目录库升级 Gate 实证。

设计保护了 TRAE 数据库，却尚未定义 Trae Sync 升级时如何迁移自己的 SQLCipher 目录库、内容图映射和 manifest 格式。应用升级中的半迁移同样可能让用户标签、版本选择和操作记录不可用。

D-042 采用旁路升级：旧目录库保持不变并只读，staging 副本逐级迁移并独立验证，验证通过后原子切换当前库指针；旧库作为受保护回滚副本保留。迁移失败继续旧库兼容只读模式并阻止全部写入。具体跨版本映射不在 V1 预先猜测，随版本更新重新讨论。

### A-019：可移动历史库与权威 manifest 的存放边界不清

状态：设计已由 D-043 解决；仍需 Gate L 覆盖自定义盘缺失、掉线、换盘、重连和迁移中断。

D-024 规定 manifest 是崩溃恢复权威依据；D-034 又允许大容量历史库迁移，并只在固定本地目录保留“恢复指针”。如果自定义历史盘在关键操作后不可用，仅有指针可能不足以判断目标数据库状态。

D-043 把进行中操作的完整权威 manifest 和最小逻辑断言固定保存在 Windows 用户本地应用数据目录，把对话目录库、大型备份与证据放在带稳定 `storage_root_id` 的自定义历史根并通过哈希引用。存储根不可用或身份不匹配时禁止新建空库、恢复和新写操作；旧根只由用户明确删除。

## 审计结论

总体架构和桌面技术栈仍然可行，项目归属迁移有真实 UI 成功证据，会话级重挂有明文与 SQLCipher 加密副本证据。A-013 至 A-019 的设计问题均已形成决策；真实 UI 继续对话仍需 Gate M，崩溃、并发、三件套、升级和存储边界仍需各自 Gate 实证。A-004 的 Gate B 事实调查和 D-044 写入权限边界已收敛；D-045 已生成实现规格与 Gate 计划，程序实现尚未开始。
