# ADR-0025：Library 抽象（主库/副库共用模块边界）

## 状态

Accepted，2026-09-04。决策来源 grill 会话（2026-09-03，主库详情页 G8+G21+G22 讨论）：用户明确要求「主库和副库的基地都是『库』，库内的东西不应耦合，后续开发副库时直接复用而非接耦重写」。

## 背景

主库（environments\master）是当前唯一的库实例：对话列表、插件、归档等模块直接以「主库」硬编码（`get_master_history` 等命令、`HistoryWorkbench` 组件命名与数据源）。规划中的副库（按账号/主题拆分的独立数据目录）落地时，若模块继续与主库实例耦合，全部功能需要接耦重写。

## 决策

1. **库是基地概念**：主库与副库都是「库」的实例。库内模块（对话列表 / 插件 / 归档 / 统计）面向「库」编程，不面向具体实例。
2. **前端注入库引用，不注入库密钥**：宿主页向库内模块注入 `libraryId`（非敏感引用字符串，如 `"master"`）。数据目录、raw key、当前 user_id 的解析全部留在 Rust 侧（AppState / 库注册表），密钥材料不经过前端——与既有安全边界一致（raw key 只存在于 Rust 进程内）。
3. **后端命令以 libraryId 参数化**：库命令接受 `libraryId`（缺省 `"master"`，兼容既有调用）。V1 库注册表只有 master 一个条目；副库落地时新增注册表条目即可，模块代码零改动。
4. **组件改名**：`HistoryWorkbench` → `LibrarySessionsPanel`（对话面板）；P8-6 删除独立历史页后，唯一宿主是主库详情页，副库详情页将来直接复用同一组件。
5. **协议事实不抽象**：SQLCipher 参数、表结构、归档通道（ADR-0022）等库内协议仍以 TECHNICAL_BASELINE 实测为准；本 ADR 只抽象「哪个库」，不重定义「库里有什么」。

## 后果

- 库命令签名多一个 `libraryId` 参数：V1 全部传 `"master"`，是纯管道改动，无行为变化。
- 副库的加密密钥管理（每库独立 raw key）在注册表设计时再定；本 ADR 只保证模块不感知。
- `LibrarySessionsPanel` 的 props 携带库描述（id + 显示名），页面标题/文案随库实例变化，数据链路不变。
