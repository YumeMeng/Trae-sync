# ADR 候选分析：WorkBuddy 凭据档案池架构

> 2026-10-18。状态：**分析稿，待用户裁决后转正式 ADR（docs/adr/ 编号）**。
> 背景：P17-T4c 已实现 WorkBuddy 独立凭据池（WBSESSN1 DPAPI 容器 + workbuddy-login 存储根 + workbuddy_capture 编排）；执行 agent 留下 ADR 级决策——独立池（现状）vs 并入 AccountRegistry 统一池。

## 事实基线（决定分析边界）

- **AccountRegistry 的语义包袱**：为 Trae 签到体系建（profile_id `checkin-*` 格式、device_id 签到配额隔离、CheckinCredentialBundle 绑定、auto_checkin_enabled/archived 等签到域字段）。Trae 切号判定、历史身份判定、签到调度**直接读它**。
- **WorkBuddy 凭据形态**：20 位平台 ID + uid(UUID)/uin(12 位)、无设备证明（零设备绑定，spec 8.8 实测）、WBSESSN1 容器、多账号并存观测（allAccounts 数组）。
- **跨产品凭据复制禁令**（T5 不变量）：凭据体系隔离是安全边界，不是实现细节。

## 方案对比

| 维度 | 方案 1：独立池（现状） | 方案 2：并入 AccountRegistry 统一池 | 方案 3：独立池 + 统一账号视图层 |
|------|----------------------|-----------------------------------|------------------------------|
| 凭据隔离 | ✅ 两套容器/两套根，污染风险为零 | ⚠️ 同一 registry 混两种容器——Trae 代码路径需要处处防 WorkBuddy 记录混入 | ✅ 同方案 1 |
| 对 Trae 现有链路的影响 | ✅ 零影响（AccountRegistry 不动） | ⚠️ **切号判定/签到调度/历史身份判定都要加产品过滤**——Trae 代码路径被扰动面大 | ✅ 零影响 |
| 多账号管理逻辑 | ⚠️ 两套（前端账号页两实现） | ✅ 一套 | ✅ 后端两套、前端统一视图（聚合层薄） |
| WorkBuddy 字段适配成本 | ✅ 零（自有结构已按形态设计） | ⚠️ AccountRecord 稀疏化改造（device proof 可空、profile_id 格式分叉、签到绑定可空）——**已上线结构被拆** | ✅ 零 |
| 迁移/演进成本 | ✅ 已上线即现状，零迁移 | ⚠️ 存量 16 Trae 档案 + 新 WorkBuddy 档案的合并迁移 | ⚠️ 需新增一个薄的聚合查询命令 |
| 与 P17 架构一致性 | ✅ 与 descriptor"差异点隔离"一致 | ⚠️ 与 T5 不变量（凭据复制禁令）张力 | ✅ 差异点隔离 + 表现层聚合 |

## 推荐结论

**方案 1（独立池，维持现状）+ 方案 3 的前端统一视图层**（按需在 T5 二期引入一个聚合查询命令，把两池账号映射为统一的账号卡片视图）。理由：

1. AccountRegistry 承载 Trae 切号/签到/历史身份的**全部判定输入**——混入异构记录的扰动面与回归风险远大于收益；
2. WorkBuddy 凭据形态（无设备证明、20 位 ID、多账号并存）与 Trae 记录**结构异构**，强行统一会把 AccountRecord 拆成"可空字段集合"；
3. 前端的统一诉求用**视图聚合**满足即可（产品并列化 T5 的分支渲染已经天然支持各产品独立面板）；
4. 未来若确需合并，独立池→统一池的迁移是**纯数据搬运**（可写一次性迁移器），反向则困难。
