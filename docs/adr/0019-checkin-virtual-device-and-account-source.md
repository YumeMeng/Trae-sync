# ADR-0019：签到设备策略与账号来源

## 状态

Accepted，2026-08-22；同日两次修订（v2 注册设备池 → **v3 有成功史设备池**，P0-y 判决实验修正 9074 根因）。**2026-08-23 生产闭环验证通过**，Phase 0 收口。吸收原 ADR-0014（签到凭据生命周期，文件已清理）的凭据写回规则（见决策第 7 条）。**2026-08-24 v4 修订**：设备池共享模型在生产中被证伪，改为"每账号独立持久设备 + 池仅作新账号一次性跳板"。**2026-08-26 v5 修订**：AuthCode 设备重铸路线实证成立，设备池体系整体退役，改为"每账号独立设备 + 9074/9095 自动重铸"。**2026-09-02 v6 修订（当前生效）**：自动重铸链退役，改为"失败即报错 + 手动重置设备"；Work 通道代码删除，全链路仅 SOLO；新增全新账号首签信任窗口协议事实（见"v6 修订动机"节与决策 1/2/8 重写）。**2026-09-09 补充**：续期阶段的 `20403` 自动恢复例外由 ADR-0027 定义，不改变 9074/9095 的手动处理规则。

## 背景

2026-08-20/21 的 HTTP 直连实验（证据在 `.scratch/checkin-http/`）确认了签到服务的三层规则：`checked_in` 展示为账号维度（CST 午夜重置）；claim 资格存在**陌生设备门禁 9074**；**设备日配额 9095**。

2026-08-22 三轮实验（P0-1 / P0-x / P0-y）裁决，P0-z 再次修正：9074 根因 = 设备 ID 无成功签到记录；编造 ID 一旦完成过真实发放即被持久信任。**直接复刻注册 API 不可行**（需 `ss_app_log` 签名）。

2026-08-25 手册实验（`.scratch/checkin-http/reports/p01-*.json`，桌面《Trae-新设备签到闭环复刻与开发手册-20260825》）发现 **AuthCode 模式设备铸造路线**：当前账号 token + `x-cloudide-token` 头请求 `GetPCAuthCode` → 全新设备四件套 → `ExchangeToken(AuthCode+PKCE)` → 新 token + 新设备绑定，无需浏览器。2026-08-26 本路线对全部 6 个生产账号完成重铸 + 当日真实发放闭环（`remint-*.json` 报告），同时实测修正了两个关键协议事实（见决策 1）。

## 决策

1. **OAuth 通道唯一化（v6 重写，取代 v5 的双形态描述）**：SOLO 通道（`en1oxy7wnw8j9n` / SOLO_PC / 完整硬件字段）是唯一使用的客户端形态——登录、铸造、续期全链路固定 SOLO。Work 形态（`ono9krqynydwx5` / IDE_PC / 空硬件字段）于 2026-09-02 从代码中彻底删除：其通道设备配额已被历史测试耗尽（20401 Device limit reached），新设备首签被 9074 稳定拒绝（2026-08-26 梦梦实测），无恢复价值。凭据包内残留的 Work client_id 解析为未知形态时按"续期必败"处理，报错引导重新登录（重新登录即产出 SOLO 凭据）。9074 含**频率维度**（时间窗风控，服务端黑盒）：v5 在老账号上实测"冷却 3-10 分钟后重试可过"；**v6 新增（2026-09-02 盈国账号实测）**：全新账号登录后的首签信任窗口更长——登录铸造后 14 分钟首签被拒、17 分钟被拒、20 分钟通过（同 SOLO 形态、同 180 秒铸签间隔，仅时间不同一败一成，证明判定变量是时间窗而非设备形态或铸造方式）。
2. **每账号独立设备 + 失败即报错（v6 重写，取代 v5 自动重铸链）**：每账号一个专属签到设备（device_id + machine_id + EC P-256 密钥对成套），长期持有。签到编排固定为 status → 单次 claim → status 复核；claim 被 9074/9095 拒绝时**不自动重铸、不自动恢复退役设备、不冷却重试**，直接报告具体业务码，由用户决定后续动作（等待后重试签到，或到账号详情页手动重置设备）。设备变更一律经用户手动发起（`reset_checkin_device` 命令：GetPCAuthCode → 全新设备四件套 → ExchangeToken → JWT 账号匹配校验 → 凭据包与注册表原子写回，失败零回写）。自动链退役理由：时间窗时长不可预测（v5 老账号 3-10 分钟、v6 新账号约 20 分钟），自动重试注定有时撞墙且每次重铸消耗服务端设备配额（20401 风险），静默等待还会造成"一直签到中"的不可感知状态。
3. **设备池体系退役（v5）**：v3/v4 的共享设备池（种子 ID/真实设备/毕业入池）、home device 毕业制、当日用量记账、降级链与回滚全部移除（`device_pool.rs` / `device_usage.rs` / `DeviceFallbackRunner` / `CheckinDeviceRebinder` 及注册表 `home_device_id` / `has_checkin_history` 字段）。池模型被 AuthCode 重铸全面替代：任何账号可随时铸造专属新设备，无需跳板。旧设备资产（种子 ID、真实设备 2490859781907946、各账号旧设备）连同凭据包备份留存于 `checkin/retired/`（含 `retired-devices.json` 清单），App 不再使用；真实设备自 v4 起与 TRAE 客户端分额的原则继续有效。
4. **账号来源仅限 App 内 OAuth 登录**：不做 Manager accounts.json 导入路径。现有账号重新授权一次换取凭据结构统一。（2026-08-26 例外记录：账号 2873473361250299 曾由 TRAE 客户端凭据导入建档，为一次性人工操作，不构成产品功能。）
5. **签到触发模型**：App 打开时自动检测各账号今日状态，设置项"打开时自动签到"默认开启；另设"全部签到"手动按钮（串行逐账号 status → 唯一一次 claim → status 复核）。Token 续期检查同样在打开时执行。不做托盘常驻、不做系统计划任务。
6. **签到结果判定**沿用已验证协议事实：HTTP 200 不构成成功；判定真实发放必须看 `checked_in` 翻转；当日已签后重复 claim 返回 code=0 但不发放（幂等空操作）；业务错误保留具体业务码语义（9074=陌生设备门禁、9095=设备日配额、1001=token 被服务端作废、20324=refresh 失效等），不得压平为单一 `business_error`。重铸链新增 `remint_failed` 原因码（重铸本身失败，旧凭据未动）。
7. **凭据写回规则**（吸收自原 ADR-0014）：续期或重铸返回的新字段，写回顺序固定为——保留旧凭据备份 → 写入临时文件 → 解密并校验账号/设备绑定 → 原子替换当前凭据 → 重新读取验证。凭据写回不得与 TRAE 进程同时修改同一凭据存储；写回失败不自动重试 `claim`、不删除旧凭据。重铸的旧设备凭据包随重铸备份至 `retired/`。
8. **编排层防护与报错语义（v6 新增）**：a) 签到命令用 try-lock 互斥——已有签到在执行时立即返回"签到正在进行中"，不静默排队（消除"一直签到中"）；b) 后端记录每账号最近一次设备重置时间戳（仅用于报错上下文，不门控不自动重试）：9074 报错按上下文区分——近期重置过→"设备刚更换，请稍候几分钟再试签到"（引导等待，避免盲目再重铸浪费配额）；未重置过→"请重置签到设备"；c) 用户可见失败文案按语义细分（9074 上下文化、9095 设备日配额、`credential_refresh_failed` 引导重新登录、20401 设备数上限），每个失败都给出可操作的下一步；d) status/claim 引入完整遥测头集合（`x-market-user-id` / `vscode-sessionid` / 每请求刷新 `x-request-id` / `x-tt-trace-id` / 固定遥测头，参照 trae-mate 开源实现），**以探针实测通过为纳入前提**（2026-09-02 grill 决议）。

## 后果

- 每账号设备配额独立（一设备一账号一签/天），账号数扩展无容量上限（随时重铸新设备）。
- 风控敞口收敛为频率维度：批量重铸场景需分钟级冷却；常规签到（有史设备）实测不受影响。
- SOLO 形态依赖完整硬件字段（本机真实描述硬编码于 `OAuthClient::Solo`，个人工具可接受；跨机器部署需重新提取）。
- 旧设备留存资产若需启用（新路线失效时的回退），恢复 `retired/` 下的凭据包备份即可。
- 若服务端进一步收紧（如 AuthCode 铸造限流、SOLO 形态新设备首签关闭），需重估重铸路线；9074 告警与手动重铸入口是安全网。

## 生产验证（2026-08-23）

首次全量生产运行（App 内"全部签到"，5 账号串行 + 随机间隔），证据 `.scratch/checkin-http/reports/p1-production-first-full-run-20260823.json`：5/5 账号当日真实发放成功。发现并修正伪数据：status/claim 响应中的 `credits` 为静态池值（恒 200），`credits_delta` 已从前端与后端全链路移除；成功权威信号 = claim code=0 + `checked_in` 翻转。

## v4 修订动机（2026-08-24）

v3 共享池模型在同日生产中被证伪：第 6 个账号签到时三个池设备当日配额已满，降级链全败且不回滚导致绑定漂移。教训：共享池与 GRILL D6 初衷自相矛盾；池容量假设未经复验即承载全部账号；失败处理缺失漂移防护。v4 回归每账号独立持久设备模型。

## v5 修订动机（2026-08-26）

手册实证的 AuthCode 铸造路线使"设备稀缺性"前提失效：任何账号可随时为自己铸造专属新设备并完成首签（SOLO 形态），设备池/跳板/毕业制的全部复杂度失去存在理由。当日对全部 6 个生产账号执行重铸 + 当日真实发放全部成功（含三次冷却重试案例），同时实测确立"SOLO 形态可行 / Work 形态被拒 / 频率维度冷却"三个协议事实。v5 删除设备池体系（代码与数据归档至 `checkin/retired/`），签到编排改为"常规签到 → 9074/9095 自动重铸 → 冷却重试一次"，注册表瘦身（移除 home/签到史字段）。旧账号全部完成 SOLO 重铸迁移，凭据包 client_id 统一为 `en1oxy7wnw8j9n`。

## v6 修订动机（2026-09-02）

v5 自动重铸链在生产中暴露三类问题（2026-09-02 grill 复盘，证据链完整）：

1. **时间窗不可预测，自动重试注定撞墙**：盈国新账号实测——同 SOLO 形态、同 180 秒铸签间隔，距登录 17 分钟的重试被 9074 拒、20 分钟的重试通过。冷却 3 分钟不是充分条件（v5 在老账号上的 3-10 分钟结论对新账号不成立），自动链的"冷却后重试一次"设计在新账号场景必然产生"重铸成功却再次失败"的循环，且每轮重铸都消耗服务端设备配额（20401 风险）。
2. **静默等待不可感知**：冷却期为进程内 `sleep(180)`，期间命令阻塞持锁；前端倒计时是组件本地状态，退出页面即丢失；重复点击静默排队等锁，用户只看到"一直签到中"。
3. **报错语义缺失**：`credential_refresh_failed` 无文案映射落入"操作未完成，请稍后重试"兜底，误导用户无限重试（当日 5 个旧 Work 凭据账号的实际出路是重新登录）。

同日确立的取证结论：Work 通道配额耗尽不可恢复，代码删除（登录/铸造/续期全链路仅 SOLO，浏览器历史取证确认 21:32 登录已走 SOLO）。v6 将设备变更权全部交还用户：失败即报错（按上下文给出可操作的下一步），重置设备为手动操作；编排层补 try-lock 快速失败与重置时间戳记录。完整请求头集合借鉴自 trae-mate（GitHub 开源，调研档案 `.scratch/handoff-trae-mate-checkin-design.md`），以探针实测为纳入前提。

## v6 决议 6 落地记录（2026-09-02 遥测头探针实测）

对 status 端点（幂等只读，不消耗 claim 名额）做带头/裸头三组对比实测——baseline（生产现状 3 头）/ with_ua（+VSCode 客户端 UA）/ full（+完整 trae-mate 头集合：固定头 `x-lscbd-aid:787976`/`app-version:0.1.54`/`x-market-client-id`/`x-user-region`/`package-type`/`x-lgw-req-sdk-type`/`x-lscbd-platform` + 账号派生 `x-market-user-id`/`vscode-sessionid` + 每请求刷新 `x-request-id`/`x-tt-trace-id`）。2 个健康账号（用户4050081350、19037135657）× 3 组全部 HTTP 200 + code=0，业务字段（enable/checked_in/credits）与基线完全一致。报告落档 `.scratch/checkin-http/reports/telemetry-headers-probe-20260902-234021.json`（runner：`cargo test -p traesync-infrastructure --test real_account_acceptance telemetry_headers_status_probe -- --ignored --nocapture`）。

据此纳入生产：`checkin_http.rs` 的 `checkin_body`（status/claim 共用）统一附遥测头集合；账号派生 ID 从设备 ID 经 SHA-256 确定性派生（同设备稳定、跨设备互异，不引入新持久状态）；每请求刷新 ID 用纳秒时钟 + 原子计数器经 SHA-256 展开。边界说明：探针仅实测 status 端点，claim 与 status 同属网关层头处理（`/trae/api/v2/ug/checkin_credits/*` 同族），风险一致可接受；`entitlement_usage`（额度查询）与 OAuth 端点未带头改造——前者维持现状，后者已有实测浏览器头（WAF 403 事实）。
