# ADR-0027：首次登录凭据验收与一次 OAuth 约束

## 状态

Accepted，2026-09-09。新增决策；依赖 ADR-0019 的设备身份、凭据原子写回与业务码透传约束。

## 背景

本次 `梦梦` 与 `用户2361650421` 的故障表明：OAuth 的 AuthCode 交换和账号身份校验成功，并不等于新凭据已经具备可持续续期能力。旧 refresh 续期路径在真实账号上返回 `20403 Token device not match`，而这时再次 OAuth 对一次性账号有明显浪费风险。

2026-09-09 的独立协议实验进一步确认：在 access token 尚未过期时，使用当前 access token、当前设备 ID 申请新的 AuthCode，再用同一设备四件套交换，可以连续成功获得新的完整凭据代次；新 access token 重新获得约 14 天寿命，配套 refresh token 重新获得约 180 天寿命。该路径不创建新设备，也不消耗第二次 OAuth。实验账号 `13347311304` 与 `15638932119` 均连续验证两次，交换后的 JWT 身份校验和写回均通过；同一批旧 refresh 的即时续期仍返回 `20403`。

## 决策

1. 首次 OAuth 产生的凭据代次必须经过本地完整性/绑定校验、账号身份校验和真实可持续性验收，且新凭据成功写回后，才向用户报告“登录完成”。验收或后续续期在 access token 仍有效时，优先使用同设备 AuthCode 滚动换发，不创建新设备。
2. 续期阶段不得把 `20403` 直接解释为需要重铸签到设备。只要当前 access token 仍有效，先使用当前设备执行 `GetPCAuthCode` → 同设备 `ExchangeToken`，以新完整凭据代次原子替换旧代次；不得自动开始第二次 OAuth。
3. 任何验收或修复失败都必须保留旧代次、候选代次和失败证据；不得把半成品凭据发布为当前代次，也不得静默覆盖可恢复材料。
4. 自动修复成功后不自动向所有账号宣称“已恢复”；账号状态以本次验收结果为准，批量修复范围与重试策略另行确认。
5. 凭据发布采用“候选代次 → 完整验收 → 原子发布”边界：候选代次在完整验收和持久化校验前不可被其他账号操作或 UI 当作当前凭据；发布时同步更新当前代次关联，任一步失败都不得产生跨文件、跨代次的半成功状态。
6. 发布事务必须写入不含 token/私钥正文的持久化发布日志，记录代次和阶段。应用启动或账号操作前只允许依据日志完成本地幂等恢复；恢复不得自动触发 OAuth、设备重铸或网络重试。
7. 对已完成登录验收的现有账号，自动维护在 access token 过期前按阈值执行同设备 AuthCode 滚动换发；每次必须整体保存新 access、refresh、过期时间和原设备材料。只有 access 已过期、无法再申请 AuthCode 时，才保留旧 refresh 签名路径作为最后兜底；该路径失败不得自动重铸签到设备或静默发起 OAuth。设备重铸仍只属于用户明确发起的签到设备变更，不改变 ADR-0019 对签到 `9074/9095` 的处理规则。
8. 手动凭据刷新是用户明确发起的立即换发：单账号每次操作最多执行一次同设备 AuthCode 换发；全部账号按账号串行执行，每个账号最多一次。手动与自动维护共用身份验收、候选代次、原子发布和失败留证边界，不因手动操作放宽 OAuth、设备或凭据完整性约束。
9. 同设备换发暂时失败但旧 access 仍有效时，按账号保留原当前凭据并采用指数退避重试（初始间隔 1 小时，逐步延长至 8 小时，之后不高于每天一次）；每日尝试次数受上限约束，超过上限后转为“凭据维护需要处理”并保留失败原因。该重试策略不得隐式发起第二次 OAuth、重铸签到设备或跨账号连带重试；手动刷新失败只返回本次结果，不启动隐藏循环。
10. 后台维护采用当前 Windows 用户下的计划任务，在用户登录时和每 6 小时唤醒一次无界面、一次性维护命令；凭据未达到阈值时不发网络请求，维护结束即退出，不常驻、不启动 TRAE、不执行签到。后台命令与 App 共用凭据互斥锁，避免并发写回。
11. 后台维护默认启用，并提供用户可见的设置开关。关闭只停止后台计划任务，不删除凭据、备份或失败证据；重新开启时恢复任务。卸载时只移除计划任务，不以此为理由删除账号材料。
12. “刷新全部账号”按账号串行执行，单个账号失败不阻断后续账号；每个账号独立保留旧当前代次并记录结果，批量完成后汇总成功、失败和无需操作的账号，不做跨账号整体回滚。

## 后果

- 登录/维护流程需要可观测的验收状态与中间证据；正常维护会在 access 过期前滚动换发完整凭据。
- 新凭据的有效期由服务端本次签发决定，不继承旧 token 的剩余寿命；当前协议实测为 access 约 14 天、refresh 约 180 天。
- 2026-09-09 用户已用两个真实测试账号确认：同设备 AuthCode 换发并写回后的凭据可以完成 TRAE Work 登录；这补齐了此前仅有接口验收、缺少桌面端闭环的证据。
- 手动刷新会产生明确的新凭据代次，因此比自动阈值检查消耗更多服务端换发请求；批量刷新必须串行且禁止隐式重复。
- 自动维护失败不会立即破坏仍有效的旧代次；退避与每日上限用于降低网络故障、服务端限流和设备绑定错误造成的重复请求风险。
- 后台维护只产生唤醒期间的短暂 CPU、内存和网络开销，不保持常驻进程；正常账号每次仅做本地检查，接近阈值时才进行换发请求。
- 续期不再通过自动重铸新设备解决设备绑定错误，避免消耗设备配额并造成签到设备漂移；签到设备重铸与凭据维护保持独立。
- 已落地的 refresh 救援门闩按凭据代次和 Profile 隔离，并用原子 `create_new` 防止应用与后台命令并发重复请求；救援失败只写账号级展示标记，不覆盖积分、额度或签到尝试证据。
- 需要把候选凭据的验证、发布和失败恢复设计成清晰的提交边界；候选发布事务与本地持久化恢复日志已确认，具体日志格式和清理策略仍待确认。

## 被否决的方案

- 仅以 AuthCode 交换成功作为登录完成：无法在首次登录时发现设备绑定失效。
- 续期失败后自动重新走 OAuth：会静默消耗一次性账号的第二次授权机会。
- 续期时自动重铸全新设备：实测新设备 AuthCode 交换后的即时 refresh 仍返回 `20403`，且会改变签到设备身份、消耗设备额度，不能作为凭据长期维护方案。
