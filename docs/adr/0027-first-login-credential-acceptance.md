# ADR-0027：首次登录凭据验收与一次 OAuth 约束

## 状态

Accepted，2026-09-09。新增决策；依赖 ADR-0019 的设备身份、凭据原子写回与业务码透传约束。

## 背景

本次 `梦梦` 与 `用户2361650421` 的故障表明：OAuth 的 AuthCode 交换和账号身份校验成功，并不等于新凭据已经具备可持续续期能力。首次真实续期才暴露出 `20403 Token device not match`，而这时再次 OAuth 对一次性账号有明显浪费风险。

## 决策

1. 首次 OAuth 产生的凭据代次必须经过本地完整性/绑定校验、账号身份校验和一次真实续期轮换，且新凭据成功写回后，才向用户报告“登录完成”。
2. 首次真实续期返回 `20403` 时，允许使用同一次登录结果中的当前 access token 自动执行最多一次设备重铸；重铸产生新的虚拟设备与完整凭据代次，并重新执行验收，不得自动开始第二次 OAuth。
3. 任何验收或修复失败都必须保留旧代次、候选代次和失败证据；不得把半成品凭据发布为当前代次，也不得静默覆盖可恢复材料。
4. 自动修复成功后不自动向所有账号宣称“已恢复”；账号状态以本次验收结果为准，批量修复范围与重试策略另行确认。
5. 凭据发布采用“候选代次 → 完整验收 → 原子发布”边界：候选代次在完整验收和持久化校验前不可被其他账号操作或 UI 当作当前凭据；发布时同步更新当前代次关联，任一步失败都不得产生跨文件、跨代次的半成功状态。
6. 发布事务必须写入不含 token/私钥正文的持久化发布日志，记录代次和阶段。应用启动或账号操作前只允许依据日志完成本地幂等恢复；恢复不得自动触发 OAuth、设备重铸或网络重试。
7. 对已完成登录验收的现有账号，续期阶段明确返回 `20403` 且当前 access token 仍能通过身份校验时，也允许对该账号当前凭据代次自动设备重铸一次；次数按代次持久记录，且仅适用于续期 `20403`，不改变 ADR-0019 对签到 `9074/9095` 的手动处理规则。

## 后果

- 登录流程会多一次真实续期请求，并需要可观测的验收状态与中间证据。
- 设备绑定失效时最多消耗一次非 OAuth 的设备重铸机会，降低二次 OAuth 对一次性账号的浪费。
- 既有账号也能在续期 `20403` 时获得一次受控的自动恢复机会，但不会因签到业务码而静默反复重铸。
- 需要把候选凭据的验证、发布和失败恢复设计成清晰的提交边界；候选发布事务与本地持久化恢复日志已确认，具体日志格式和清理策略仍待确认。

## 被否决的方案

- 仅以 AuthCode 交换成功作为登录完成：无法在首次登录时发现设备绑定失效。
- 续期失败后自动重新走 OAuth：会静默消耗一次性账号的第二次授权机会。
