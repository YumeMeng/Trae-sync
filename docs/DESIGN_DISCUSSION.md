# Trae Sync 设计讨论记录

## 讨论规则

- 一次只决定一个问题。
- 能从代码或数据库确认的事实不询问用户。
- 每个决策记录推荐答案、取舍和用户结论。
- 达成共享理解前不进入实现。

## 产品目标

开发一个独立桌面工具，自动发现本机 TRAE 系列产品和本地对话数据，建立中立的本地历史库，并让活动数据库中选定项目的历史归属跟随当前登录账号。

工具首版参考现有 Tauri 账号管理器的桌面形态，但不依赖其账号存储、Token 或切换实现。

## 已确认决策

### D-001：历史库不绑定主账号

状态：已确认。

结论：

- 建立永久中立的“本地历史库”。
- 所有发现的对话先进入本地历史库。
- TRAE 账号只作为扫描来源和同步目标。
- 不要求用户选择永久“主账号”。
- 工具界面不把数据库、`user_id` 或分库作为主要使用概念。

用户主要看到：

```text
本地历史库
当前 TRAE 产品与当前账号
同步范围
同步预览和结果
```

## 推荐产品流程

```text
自动发现 TRAE 产品
识别当前账号和本地数据库
扫描并收入本地历史库
浏览账号、项目和会话
选择同步范围
选择当前登录账号作为目标
预览新增、重复和冲突
备份目标数据库
让所选历史跟随当前账号
验证并允许回滚
```

## 推荐模块边界

```text
Product Adapter
Scanner
Local Library
Sync Planner
Sync Executor
Backup and Restore
Desktop UI
```

`Product Adapter` 隔离不同 TRAE 产品的数据目录、进程、账号检测、密钥和 schema 差异。

## 逐项决策记录

### D-002：本地历史库的真实存储模型

状态：已确认。

结论：采用双层模型。

1. 不可变来源快照：保存每次扫描得到的原始 DB/WAL/SHM 和来源元数据，用于恢复、重新解析和应对未来 schema 变化。
2. 规范化目录库：提取账号、项目、会话、时间、标题和内容索引，用于浏览、搜索、去重和生成同步计划。

不可变快照是最终证据；规范化目录库是可重建的产品视图。

备选方案：

- 只存完整数据库快照：恢复可靠，但难以选择性合并和搜索。
- 只存规范化记录：占用较小，但首次解析遗漏的数据以后无法恢复。

原始快照是不可变事实来源；规范化目录库允许删除后从快照重建。D-021 已确认快照不自动删除；V1 在数据指纹未变化时不创建重复快照，也不做跨快照物理文件去重，避免引入共享引用删除风险。

### D-003：首版同步选择粒度

状态：已由 D-037 重新确认；V1 支持账号、项目和单条完整对话三级自定义选择。

结论：首版同步范围提供：

```text
全部历史（动态包含新发现的可同步项目）
自定义（按来源账号、项目或单条完整对话选择）
```

任务列表中的单个标题及其全部内容对应一个会话。会话始终可以在历史库中逐条浏览和搜索。

原理由认为单会话同步必须复制消息、turn、history、task、snapshot、FTS 和正文 JSON。D-037 已证明这只适用于“创建第二份独立副本”，不适用于“让现有会话跟随目标项目”。后者保留所有内容 ID，只重挂会话的项目关系。

普通工作台默认使用“全部历史”，不显示大量选择项；只有用户进入“自定义”后，才按“账号 -> 项目 -> 对话标题”展开三级选择。

### D-004：同步结果是合并还是镜像覆盖

状态：已确认。

结论：V1 在目标账号一侧形成非破坏性并入，底层使用项目归属转移或活动会话重挂，不是双账号同时拥有独立副本：

```text
目标账号原有历史
+ 本次转入的选中活动历史
= 当前账号同步后可见历史

来源账号不再显示已转入项目或会话
本地历史库继续保留来源、快照和操作记录
```

默认规则：

- 不删除目标账号已有历史。
- 不用来源快照整体覆盖目标数据库。
- 不复制或重写会话、消息和完整关系图；目标没有同一项目时修改选中完整项目的 `project.user_id`，目标已有同一项目时只重挂计划内活动会话的项目关系。
- 被转入项目或会话会从原账号的当前可见历史中移走；以后切回该账号时可以再次执行跟随操作。
- “非破坏性”表示不删除历史内容且可通过再次转移或备份恢复，不表示两个账号同时持有相同项目。
- 完全相同的历史跳过。
- 同一逻辑历史存在不同版本时标记冲突，先不覆盖。
- “替换目标历史”只能作为未来明确命名的高级操作，不能混入普通同步。

“替换目标历史”不进入 V1。

### D-005：同一会话的逻辑身份

状态：已确认。

结论：使用以下逻辑键：

```text
(product_history_namespace, original_session_id)
```

规则：

- `original_session_id` 使用 TRAE 原始 `chat_session.session_id`。
- 来源账号不进入逻辑键；会话在账号间转移后仍是同一会话。
- 安装目录和机器不进入逻辑键；复制到另一目录或机器后仍可去重。
- 标题、时间和内容哈希不作为身份；这些字段可能正常变化。
- 内容图哈希用于标识会话版本，不用于标识会话本身。
- `product_history_namespace` 由 Adapter 定义，避免不兼容的 TRAE 产品误认成同一会话。

如果同一逻辑键出现不兼容内容，作为版本冲突处理，而不是创建两个无关会话。

内容图哈希只负责区分该逻辑会话的不同版本。

### D-006：会话版本推进和分叉冲突

状态：已确认。

结论：把同一逻辑会话的两次扫描分为三类：

```text
完全相同
可快进版本
分叉冲突
```

处理规则：

- 完全相同：规范化内容图哈希一致，直接去重。
- 可快进版本：共享稳定 ID 的内容一致，一份记录只是另一份的严格扩展；自动把扩展版本设为当前版本，旧快照继续保留。
- 分叉冲突：共享稳定 ID 的正文不同、双方各有独有分支，或存在无法证明安全的删除/重写；保留两个版本，不自动拼接或覆盖。
- 分叉冲突属于历史库版本浏览语义；V1 跟随操作只使用活动数据库中项目的当前实际状态，不尝试把某个归档版本写回 TRAE。
- 用户选定版本只改变“当前投影版本”，不删除另一份来源快照。

具体内容图和比较规则由 D-031 定义，不向用户暴露为可调参数。

这种规则允许持续增长的正常会话自动更新，同时避免用“时间较新”静默覆盖另一条有效分支。

冲突选择只改变规范化目录库中的当前投影，原始快照保持不可变。

### D-007：自动检测、扫描和同步的触发边界

状态：已确认，并接受用户隐私控制修正。

结论：采用“检测可授权自动化，扫描默认手动，写入始终手动”：

- 首次使用先说明将读取的产品目录、账号标识和对话数据库，并请求扫描授权。
- “安全时自动扫描”作为设置开关，默认关闭。
- 用户未开启自动扫描时，只在点击“扫描历史”后读取对话数据库。
- 用户开启后，启动工具时自动检测 TRAE 产品、数据库、当前账号和数据指纹。
- 数据指纹未变化时不重复扫描。
- 数据发生变化且 TRAE 已关闭时，自动建立新快照并更新目录库。
- TRAE 正在运行时不复制不稳定的 DB/WAL/SHM；界面提示关闭后扫描。
- 每次同步前强制重新检测目标状态、刷新快照并建立目标备份。
- 修改目标数据库的同步操作必须由用户明确点击并确认预览。
- V1 不在后台监听账号变化后自动写库，也不与账号管理器建立自动切换联动。

关闭自动扫描不会影响手动扫描、同步预览、备份或恢复能力。无论开关状态如何，工具都不能自动执行数据库写入。

### D-008：账号检测与账号管理边界

已查明事实：当前实际 TRAE Work CN `storage.json` 中的认证值不是参考项目所假设的明文嵌套 JSON，而是 Base64 包装的 `tc` 二进制密文。独立工具不能依赖 `Trae-Account-Manager-main` 的 `accounts.json`，也不从已被同步修改的 `project.user_id` 猜测。

Gate B 已通过 10 个真实启动会话确认当前账号可由严格白名单日志事件解析，并与认证字段不可逆指纹及 Local Storage 账号作用域绑定。认证密文不需要在 V1 直接解密。详细证据见 `docs/ACCOUNT_DETECTION_FEASIBILITY.md`。

状态：已确认。

结论：V1 边界：

- 从 TRAE 自身数据中检测当前 `user_id` 和可用显示信息。
- 只保存“已见账号目录”：账号 ID、用户标签、来源产品和最近发现时间。
- 不保存 Token、refresh token 或 cookies。
- 不负责登录或切换账号。
- 用户要同步到另一账号时，先在 TRAE 或现有账号管理器完成切换，再回本工具刷新当前账号。
- 自动检测失败时，不根据 `project.user_id` 猜测当前账号；手工选择已见账号只能用于历史整理和显示，不能解锁目标数据库写入。写入必须先取得 D-044 定义的新鲜账号证据。
- 后续可定义外部账号管理器集成接口，但不改变历史工具的凭证边界。

这样可保持工具独立，也避免为了历史同步复制一套认证和账号切换系统。

未来外部账号管理器集成只能通过可选接口完成，不能让核心历史库依赖账号管理器。

### D-009：多 TRAE 产品的首版范围

状态：已确认，并补充平台切换入口要求。

结论：采用“单产品交付、Adapter 架构预留”：

- V1 只实现并交付 TRAE Work CN / TRAE SOLO CN Adapter。
- 核心从第一天通过窄 `ProductAdapter` 接口调用产品能力。
- Adapter 负责产品路径发现、进程状态、当前账号解析、数据库快照、密钥参数、schema 探测、读取和写入映射。
- 核心负责本地历史库、版本去重、同步计划、备份编排、操作日志和 UI。
- TRAE IDE Adapter 必须先独立完成路径、密钥、schema、账号检测和写回验证，再接入；不能假设它与 Work CN 相同。
- 平台上下文是一级 UI 状态；主界面或设置中始终提供平台选择/管理入口。
- 平台下的数据目标按照 D-028 建模为“数据位置”；只有一个位置时不增加多余选择步骤。
- 平台选择器只列出已安装且已实现的 Adapter；V1 通常只有 TRAE Work CN。
- 平台切换会切换扫描来源、当前账号、历史命名空间、同步目标和平台设置。
- 未实现的 TRAE IDE 不作为可选目标，避免用户进入不可工作的流程。

这样保留扩展方向，同时避免用未经验证的第二产品污染首版数据契约。

### D-010：本地历史库的静态加密

已知影响：不可变来源快照可保持 TRAE 原始加密，但规范化目录库需要保存可浏览、可搜索的对话正文。如果使用普通 SQLite，它会在磁盘留下明文历史。

状态：已确认。

结论：

- 规范化目录库使用 SQLCipher 加密。
- 首次创建历史库时生成随机库密钥，不复用 TRAE 固定 raw key。
- Windows V1 使用当前系统用户的 DPAPI 保护库密钥，正常启动无需输入密码。
- 密钥不写入配置明文，也不依赖账号 Token。
- 原始快照保持原文件字节和来源哈希，不提前永久解密保存。
- D-029 在 V1 提供只备份目录库密钥的加密恢复包；包含历史正文的完整便携归档仍留到未来版本。

备选方案：

- 每次启动输入主密码：控制更强，但日常使用摩擦明显。
- 明文目录库：实现最简单，但与用户对扫描隐私的顾虑冲突。

包含历史正文的便携归档和每次启动都输入的主密码不进入 V1；D-029 的恢复密码只在导出或导入恢复包时使用。

### D-011：生产程序中的 SQLCipher 集成方式

状态：已确认。

结论：由 Rust 后端嵌入并固定 SQLCipher 版本：

- 使用 Rust SQLite 绑定连接随程序构建的 SQLCipher。
- 优先静态或 vendored 链接，避免依赖系统已安装 DLL。
- 运行时校验 `cipher_version` 和目标库参数。
- 工具目录库和 TRAE 目标库共用连接基础设施，但使用独立 key provider 和 schema adapter。
- 数据库操作通过进程内事务和结构化错误完成，不用 shell 拼接 SQL。
- Docker 和 SQLCipher CLI 只允许用于开发期研究、交叉验证和故障诊断。
- 生产程序不要求用户安装 Docker，不启动外部 CLI，也不调用 TRAE 自带 `ai_agent.dll`。

取舍：嵌入构建比调用 CLI 更难配置，但能获得可控版本、事务、取消、错误处理和正常桌面安装体验；调用 TRAE DLL 会绑定私有 ABI 和安装版本，不适合作为独立工具基础。

具体 Rust crate、链接方式和构建环境必须通过实现前技术 Gate 验证。

### D-012：写入前备份是否强制

状态：已确认。

结论：所有目标数据库写入都必须先完成不可变备份，且此项不能关闭：

- 保存目标 `database.db`、`database.db-wal`、`database.db-shm` 原始证据快照。
- 通过 SQLCipher 连接和 SQLite Backup API 生成单文件逻辑恢复副本。
- 用独立连接打开逻辑恢复副本并完成两层完整性检查。
- 记录来源产品、数据路径、当前账号、schema 指纹、文件哈希、同步计划和创建时间。
- 备份完成后重新比较源文件指纹；发生变化则废弃该计划并重新预检。
- 任一复制或哈希失败时，不开始同步事务。
- 恢复备份前也先保存当前状态，避免回滚操作本身造成不可逆丢失。
- 恢复仅在目标 TRAE 已停止时执行，并在恢复后重新打开、验证数据库。
- UI 提供“操作记录”和“一键恢复此操作之前的状态”。

自动扫描可由用户关闭，但写前备份属于数据库写入事务的必要条件，不作为隐私或性能开关。

写前备份是 Sync Executor 的前置阶段，不由具体 Product Adapter 自行决定是否跳过。

### D-013：备份保留、固定和空间警戒线

当前 Work CN 数据库约为 257 MB；如果每次扫描都永久保留完整快照，磁盘占用会快速增长。

状态：已确认，并由 D-021 修正自动清理规则。

结论：

- 默认全局历史存储警戒线为 5 GB，用户可调整；它不是自动删除配额。
- 工具永不自动删除快照、写前备份、冲突版本或规范化历史。
- 达到警戒线后暂停非必要自动扫描，已有数据保持不动。
- 首次基线、最近成功写前备份、当前快照和冲突来源默认保护。
- 用户手动固定的快照默认保护。
- 用户拥有最终删除权：可显式解除保护，再经过影响清单和二次确认删除。
- 删除记录进入操作日志，但不能由同步流程或空间任务顺带触发。
- 设置页显示总占用、各平台占用、保护状态，并提供迁移目录和手动管理。

设置页默认直接采用 5 GB 推荐值；调整入口放在“存储管理”详情中，不要求用户首次使用时配置。
Trae Sync 自己的大容量历史数据使用一个统一存储根目录；用户可以在存储管理中选择其他本地磁盘，具体迁移规则由 D-034 定义。

“严格防止数据丢失”约束工具的自动行为；用户明确知情后的删除选择仍被尊重。

### D-014：应用主信息架构

状态：已确认。

结论：应用直接打开“同步工作台”，不做欢迎页、数据仪表盘或账号卡片首页。

持久导航：

```text
平台选择器
同步
历史库
操作与备份
设置
```

同步工作台从上到下提供：

```text
当前平台与当前账号状态
最近扫描状态和刷新操作
同步范围：[全部历史 | 自定义]
自定义范围：来源账号 / 项目
选中内容摘要
同步预览
明确的“应用到当前账号”命令
```

交互规则：

- 平台选择器始终可见。
- 当前账号是目标状态，不表现成可在本工具登录的账号卡片。
- 原始 `user_id`、数据库路径和 schema 只放在详情或诊断视图。
- “应用到当前账号”先生成计划和归属变化预览，再进入确认，不直接写库。
- 历史库负责浏览、搜索、来源和版本；不把同步命令散落到每条会话。
- 操作与备份合并展示同步结果、失败、备份和恢复入口。
- 首次无数据时，工作台直接提供“扫描历史”，不展示产品介绍页面。

具体布局和视觉稿在行为规格确认后单独设计。

### D-015：同步预览分类与事务原子性

状态：已确认。

结论：同步预览按项目汇总选中的项目或会话动作：

```text
将跟随当前账号
已在当前账号，自动跳过
项目身份或路径冲突
部分会话缺少可重挂的目标项目
仅归档，暂不能应用
活动数据库版本不兼容
```

执行规则：

- 历史库会话分叉不参与 V1 项目归属执行；项目身份冲突、仅归档和活动数据库不兼容项默认排除，不阻止其余可同步项目。
- D-027 定义的项目身份、同目录和无法判定冲突同样默认排除，不阻止其余项目同步。
- 用户确认的是明确列出的项目归属移动和会话并入动作集合。
- 对同一个目标数据库，全部确认动作在一个事务中执行。
- 运行中任一断言、写入或验证失败，整个写入事务回滚，不保留半成功状态。
- “已在当前账号”与“预先排除”属于计划结果，不算运行时失败。
- 同步完成页分别显示已同步、已跳过、待处理和失败数量，并关联写前备份。

即：计划阶段允许排除问题项，执行阶段保持全有或全无。

Sync Executor 只能执行已经固化并带目标指纹的计划；目标状态变化时必须回到预览阶段。

### D-019：桌面技术栈与首版操作系统

状态：已确认。

结论：

- 独立项目路径：`D:\work\Trae-sync`。
- Tauri 2 作为桌面外壳。
- Rust 后端负责 Product Adapter、快照、SQLCipher、目录库、同步事务、备份和恢复。
- React + TypeScript + Vite 负责桌面 UI。
- 核心业务模块不依赖 Tauri command；Tauri command 只做薄适配，便于单元和集成测试。
- 前端不直接访问数据库、文件系统或账号认证文件。
- V1 只支持 Windows x64 和本机 TRAE Work CN。
- OS 路径、DPAPI、进程控制放入 Windows 平台层；不在核心模型中散布 Windows 条件。
- macOS、跨设备和远程同步不进入 V1。

这复用当前项目已经证明可工作的桌面技术方向，但新项目不复制账号管理器业务代码。

#### 桌面框架适配性分析

该产品必须完成本地进程检测、正常关闭应用、复制大文件、DPAPI 密钥保护、SQLCipher 事务、哈希校验和恢复。纯 Web 应用无法合理获得这些能力，桌面应用形态正确。

| 方案 | 适配性 | 主要判断 |
| --- | --- | --- |
| Tauri 2 + Rust + React | 推荐 | Rust 适合文件、进程、DPAPI、FFI 和事务；React 适合历史浏览和同步预览；安装体积和运行内存低于 Electron |
| Electron | 可行但不推荐 | Web 生态成熟，也可能更接近 TRAE 的认证存储格式；但运行体积大，Node 原生 SQLCipher 模块打包和 ABI 管理仍复杂 |
| WPF / WinUI | Windows 能力强 | DPAPI 和系统集成直接，但未来 macOS 成本高，也无法复用当前 Rust/React 技术经验 |
| Flutter | 不优先 | UI 跨平台强，但 SQLCipher、DPAPI 和 Windows 进程能力仍需原生插件，增加两套边界 |

Tauri 的主要风险不是 UI，而是原生依赖构建和长任务编排：

- 需要证明 vendored SQLCipher 能在 Windows 构建、打包并打开真实副本。
- 需要把 Gate B 已验证的日志、认证指纹和 Local Storage 组合证据实现为 Windows Adapter，并通过异常 fixture。
- 大数据库哈希、快照和完整性检查必须在后台工作线程执行，并向 UI 报告阶段进度，不能阻塞 Tauri 主线程。
- 中途取消和阶段进度遵循 D-033；进入写事务后应完成验证或恢复，不能直接杀死任务。
- WebView2 运行时需要在安装器中检测和引导安装。

实现前技术 Gate：

```text
Gate A：Tauri/Rust 内嵌 SQLCipher 打开真实加密副本并通过完整性检查
Gate B：Windows Adapter 识别当前账号，不保存 Token
Gate C：大文件快照、哈希、事务和恢复可重复通过
Gate D：前端能显示长任务进度、失败阶段和恢复入口
```

结论：Tauri 2 适合并能较好完成任务。项目成败主要取决于 Product Adapter 和数据库操作 Gate，不取决于桌面 UI 框架。四个 Gate 是正式功能开发前置条件。

### D-020：每次写入后的完整性验证深度

已知取舍：完整 `cipher_integrity_check` 和 `integrity_check` 会扫描大部分或全部数据库，当前约 257 MB 的库可能产生明显等待；只查数量和目标行更快，但不能发现其他页或 B-tree 损坏。

状态：已确认，并上升为严格数据保全要求。

结论：

- 写事务内执行迁移数量、唯一约束和关系覆盖断言。
- 提交后用新连接验证 key、schema、目标账号、项目、会话和消息数量。
- 每次写入后强制执行完整 `cipher_integrity_check` 和 `integrity_check`。
- 完整检查结束前，操作状态保持“正在验证”，不报告成功，也不重新启动 TRAE。
- 完整检查失败时按照 D-025 的受控恢复协议处理；不能未经分类和取证就直接覆盖目标。
- V1 不提供跳过完整验证的“快速模式”。后续只有性能数据证明等待不可接受时，才讨论分级验证。
- 完整检查的阶段展示和取消边界由 D-033 定义，不使用无法证明的百分比。

这样牺牲部分速度，换取对数据库写入工具更重要的确定性。

全局原则：任何便利、性能或空间优化都不能静默牺牲已扫描历史、目标原数据或恢复能力。

下列是本轮决策时确定的核心 Gate；D-045 生成的 `docs/GATE_PLAN.md` 是完整 Gate 集合和依赖关系的当前权威文档。

#### V1 验收标准

1. 未授权扫描时不读取对话数据库；关闭自动扫描后只响应手动扫描。
2. 扫描不修改 TRAE 原文件，来源和快照哈希一致。
3. 目录库磁盘内容不是明文 SQLite，对话正文和库密钥不以明文配置保存。
4. 重复扫描、会话增长和分叉 fixture 分别得到去重、快进和冲突结果。
5. 预览计划绑定目标数据库指纹；目标变化后旧计划不能执行。
6. 同步前按实际存在性保存并验证 DB/WAL/SHM 原始证据，同时生成并独立验证逻辑恢复副本；任一失败时目标数据库零写入。
7. 测试副本同步后，目标尚无同一项目时完整项目归属目标账号；可靠同一项目中的选中会话挂到目标项目；目标原历史仍存在，来源账号不再显示已转入内容，排除项未改变。
8. 唯一键冲突、进程重新启动、磁盘空间不足和中途异常均不会留下半事务结果。
9. 写后两层完整性检查通过才报告成功；失败路径恢复后匹配写前逻辑断言并可完整打开，原始失败现场和写前证据保持可验证。
10. 恢复操作先备份当前状态，恢复后重新验证；用户可从操作记录找到对应前后状态。
11. 工具永不自动删除历史或备份，达到警戒线只暂停非必要自动扫描。
12. 真实 Work CN 副本完成端到端演练后，才允许一次明确授权的真实库验收。

### D-023：写前双备份格式

状态：已确认。

结论：每次写前同时创建：

```text
原始证据快照：database.db + database.db-wal + database.db-shm 原字节和哈希
```

- 恢复后不复用旧 SHM；由 SQLite 根据恢复后的 DB/WAL 状态重新建立瞬态共享内存。

### D-024：跨库操作的崩溃恢复协议

状态：已确认；具体状态名和终态已由 D-039 统一。

结论：采用持久化操作状态机和权威操作 manifest，解决目标 TRAE 数据库与工具目录库无法共享一个事务的问题。

```text
planned
backup_verified
target_writing
target_committed
target_verified
catalog_reconciled
completed
restore_required
restored
```

规则：

- manifest 是崩溃恢复的权威依据；目录库只镜像其状态用于查询和界面展示。
- 每个阶段持久化操作 ID、同步计划、目标数据库指纹、写前/预期写后指纹、备份 ID 和已完成阶段。
- 阶段状态必须先以临时文件完整写入并落盘，再通过同卷原子替换发布，避免 manifest 自身留下半写状态。
- 应用启动时先扫描所有未完成操作，完成协调前禁止对同一目标开始新写操作。
- 永不盲目重放 `target_writing` 或其他写事务；先在 TRAE 关闭状态下读取目标指纹并与 manifest 对照。
- 目标匹配写前指纹时，认定目标写事务未提交或已回滚，保留记录并结束为未应用状态。
- 目标匹配预期写后指纹时，继续执行完整性验证和目录库协调，不再次写入目标。
- 目标不匹配任一已知指纹时立即停止，标记 `restore_required`，进入人工确认的恢复流程。
- `completed` 仅在目标完整性验证通过且目录库已协调后写入。
- Gate C 必须在每个阶段注入进程崩溃，验证重启后不会重复应用、遗漏已提交结果或错误报告成功。

### D-025：写后验证失败的受控自动恢复

状态：已确认，并要求优先保证用户体验；恢复状态已并入 D-039 的唯一状态机。

结论：写后验证失败不立即覆盖目标。系统先判定失败类型并保护现场；只有恢复安全性得到完整证明时才自动恢复，正常情况下不要求用户理解数据库细节或手动选择文件。

处理规则：

1. 关闭所有数据库连接并保持 TRAE 停止，manifest 记录验证输出和当前目标指纹。
2. 使用新连接重新执行验证，以区分明确的完整性失败与锁定、权限、临时 I/O 等“验证未完成”。
3. 验证未完成时不覆盖目标，进入 `verification_inconclusive`；允许排除环境问题后重试验证。
4. 明确完整性失败时进入 `restore_required`，先保存失败后的 DB/WAL/SHM 原始证据快照并逐文件计算哈希。
5. 再次独立打开并完整验证本次写前逻辑恢复副本；验证失败则停止自动恢复。
6. 在目标同卷 staging 路径生成恢复文件，完整验证并落盘后进入 `restore_staged`。
7. 目标仍匹配 manifest 记录的失败后指纹时，才执行受状态机保护的替换；指纹变化则停止自动恢复。
8. 替换后用新连接执行目标身份、schema、记录断言、`cipher_integrity_check` 和 `integrity_check`。
9. 全部通过后进入 `restored_verified`，本次同步显示为“未应用，已恢复同步前状态”，不能显示成功。
10. 任一前置条件、取证、staging、替换或恢复后验证失败，进入 `manual_recovery_required`；不继续覆盖、不启动 TRAE，并保留全部前后证据和已验证备份。

恢复相关持久化状态补充为：

```text
verification_inconclusive
restore_required
failure_snapshot_verified
restore_staged
restore_replacing
restored_verified
manual_recovery_required
```

用户体验规则：

- 正常恢复只显示可理解的阶段：`正在验证同步结果`、`发现异常，正在保护数据`、`正在恢复同步前状态`、`恢复完成，本次同步未应用`。
- 技术错误、文件路径、哈希和 PRAGMA 输出收进可展开详情与诊断报告，不要求用户据此作判断。
- 阶段进度必须来自真实状态，不显示虚假百分比；恢复耗时较长时应用仍保持响应。
- manifest 在每阶段落盘，因此应用意外退出后能继续判断和恢复，不要求用户从头重做同步。
- 自动恢复期间不弹出无意义的重复确认；只有进入 `manual_recovery_required` 时才显示明确原因和经过验证的可用操作。
- 失败后证据、写前备份和恢复日志永不自动删除。
- 恢复验证完成前禁止自动重启 TRAE。
- Gate C 必须覆盖完整性失败、验证未完成、取证失败、staging 失败和替换中崩溃，并验证每种情况不会丢失写前或失败后的数据。

### D-029：DPAPI 失效后的加密恢复包

状态：已确认。

结论：V1 提供可选但明确推荐的 `.traesync-recovery` 恢复包。日常启动仍由 Windows DPAPI 无感解锁；恢复密码只在导出和灾难恢复时使用。

范围：

- 恢复包只包含被密码加密的目录库 SQLCipher 随机密钥、目录库 ID、密钥代次、格式版本、KDF 参数和认证加密所需元数据。
- 恢复包不包含对话正文、原始快照、账号 Token 或 TRAE 数据库固定密钥。
- 恢复包虽然不含正文，但能够解锁对应目录库，因此 UI 必须明确提示其敏感性。
- 包格式必须版本化并使用带认证的加密；密码通过内存困难 KDF 派生，具体参数由实现 Gate 按目标 Windows x64 设备基准确定并写入包内。

创建与日常体验：

- 首次成功建立目录库后提示一次“创建历史库恢复包（推荐）”，允许跳过，不阻断扫描或同步。
- 设置页持续显示“已创建”“未创建”或“需要更新”，不重复弹窗打扰。
- 导出时要求用户设置并确认恢复密码，选择保存位置；建议选择其他磁盘或外部介质，不默认保存到历史库目录。
- KDF、加密算法、密钥代次和格式版本全部使用程序内置的版本化推荐值，不作为用户配置项。
- 工具不能上传、代管或记录恢复密码，也不自动复制恢复包到云端。
- 目录库密钥未变化时无需随每次扫描重新导出；密钥轮换后旧包标记为过期并提示重新创建。
- 用户可以创建多个同代次恢复包；工具不自动删除任何旧恢复包。

恢复规则：

- DPAPI 解锁失败时进入只读恢复入口，不新建同名空目录库掩盖原故障。
- 用户选择目录库、恢复包并输入密码后，先验证包的认证标签、目录库 ID 和密钥代次。
- 使用恢复密钥只读打开原目录库并执行完整性检查；成功前不覆盖目录库、不替换现有 DPAPI 密钥包装。
- 验证通过后才把同一目录库密钥重新使用当前 Windows 用户的 DPAPI 保护，并记录恢复操作。
- 当前存在另一目录库时，先备份并要求用户明确选择要打开的库；恢复流程不能静默合并或覆盖两个目录库。
- 密码错误、包损坏、目录库不匹配或完整性验证失败时保持原文件不变，并给出可重试的明确原因。

用户未创建恢复包时，原始快照仍可用于重建可解析的历史内容，但用户归类、版本选择和部分操作记录可能无法从快照完全恢复；界面必须如实说明这一差异。

Gate H 必须演练 DPAPI blob 丢失、正确/错误密码、损坏恢复包、错误目录库、密钥轮换和新 Windows Profile 重新包装，验证恢复不会覆盖错误目录库或产生明文密钥文件。

### D-031：会话版本的规范化内容图

状态：已确认。

结论：版本比较采用 Adapter 内置、版本化的规范化内容图和保守判定，不提供用户调参。原始快照始终保留，任何无法证明安全的情况都不会被自动覆盖或拼接。

默认分类：

```text
语义内容图完全相同                       完全相同，自动去重
旧图全部语义节点和关系不变，新图只增加内容  可快进，采用更完整版本
已有语义内容被修改、删除或重新排序          分叉冲突，保留两个版本
只有已确认的易变或派生字段变化              仍视为同一内容版本
schema 或字段语义无法可靠判断               未分类，保留两个版本
```

规范化规则：

- Work CN Adapter 按真实 schema 明确列出稳定 ID、语义字段、易变字段、派生字段和有序关系，映射本身带版本号。
- 会话、消息、turn、history、task、snapshot 及其引用是否进入内容图，必须通过真实数据关系确认，不能仅根据表名猜测。
- 语义节点以稳定 ID 标识；字符串、数字、空值和 JSON 使用确定性编码后再计算摘要，不能直接依赖 SQLite 行顺序或原始 JSON 键顺序。
- 消息和 turn 等有序内容必须比较稳定顺序关系；只有新增内容且所有既有节点、语义字段和关系保持不变时才是严格扩展。
- `updated_at`、FTS、缓存、索引和已证明可重建的派生摘要不触发正文分叉，但其原值仍保留在不可变快照中。
- 标题等展示元数据单独保留观察历史；仅标题变化不把正文误判为分叉，当前展示使用最近有效观察值。
- 未识别字段、新表、缺失稳定 ID 或 Adapter 映射版本不兼容时，不盲目忽略，标记“暂时无法比较”。
- 用户选择某个分叉版本只更新目录库当前投影，不删除、改写或合并其他版本和来源快照。

用户体验规则：

- 普通扫描结果只显示“无变化”“新增内容”或“存在不同版本”，不显示表、字段或哈希。
- 无变化和严格扩展自动处理；只有真实分叉或未分类版本需要用户在历史详情中选择。
- 未选择的分叉版本仍可浏览并长期保留；同步预览默认排除尚未选择的冲突内容。
- Gate I 必须使用真实重复扫描 fixture 覆盖无变化、正常追加、标题变化、正文修改、删除、重排、派生字段变化和未知 schema，验证不会误覆盖有效版本。

结论：V1 不恢复、不物理删除也不单独迁移软删除内容。项目级归属变更保持活动项目完整关系图中的软删除子记录原样，但普通界面和同步数量只计算仍可见的历史。

规则：

- `project.deleted_at` 已标记的整个项目不进入同步计划，仍保留在原始快照和诊断统计中。
- 活动项目中的软删除会话、消息及其他子记录保持原行、关系和删除标记不变。
- Sync Executor 只修改计划确认的项目归属或会话项目关系字段，不清除 `deleted_at`、不复制隐藏内容为新记录，也不为排除软删除子记录而拆解项目图。
- 项目归属变化后，软删除子记录可能仍通过关系属于该项目；这表示底层数据被完整保留，不表示其可见状态被恢复。
- 同步预览和完成页的项目、会话、消息数量只统计按 Work CN 正常可见条件查询得到的内容。
- 软删除行数量仅放在可展开诊断详情、备份清单和完整性断言中，不混入普通成功数量。
- 写前备份、写后关系断言和完整性检查覆盖所有行，包括软删除内容，确保同步没有意外丢失或改变它们。
- 软删除状态在后续扫描中属于语义变化，按照 D-031 的版本规则保留对应快照；V1 不提供恢复可见性的操作。
- Gate J 必须覆盖软删除项目、软删除会话、软删除消息和混合活动项目，验证 UI 统计、底层行数与删除标记在同步前后符合上述规则。

### D-033：长任务的真实阶段进度与取消边界

状态：已确认。

结论：完整验证保持强制开启；界面使用真实阶段和可测进度，不提供“快速模式”或检查等级配置。

用户可见阶段：

```text
正在准备
正在备份
正在写入
正在验证
已完成 / 正在恢复
```

进度规则：

- 文件复制、哈希和其他具有确定总字节数的步骤显示真实已处理量和进度。
- SQLCipher `cipher_integrity_check`、SQLite `integrity_check` 等没有可靠总工作量的步骤只显示当前阶段和已用时间，不伪造百分比或承诺完成时间。
- UI 只展示面向用户的阶段；具体子步骤、页数、PRAGMA 输出和性能计数放在诊断详情。
- 所有长任务在 Rust 后台工作线程执行，通过结构化事件更新 Tauri 前端；不能阻塞主线程、窗口交互或最小化。
- 相同阶段事件必须节流，避免大文件处理时用高频消息拖慢任务。

取消和关闭规则：

- 读取、规划以及目标写事务开始前的备份阶段允许请求取消；取消后不修改目标，已经完成的备份仍保留且不自动删除。
- 一旦进入 `target_writing`，取消按钮变为不可用；任务必须继续到提交后验证、事务回滚或受控恢复的安全终态。
- 关键阶段请求关闭窗口时记录“完成当前数据保护步骤后退出”，界面继续显示状态，不能直接终止后端任务。
- 操作系统关机、断电或进程被外部终止无法由 UI 阻止，重启后由 D-024 manifest 恢复协议接管。
- 写入、验证或恢复完成前不重新启动 TRAE；用户可以最小化工具并继续等待。

Gate K 必须在本机真实约 257 MB 数据库副本和较慢存储场景中记录各阶段耗时、事件频率、内存占用和 UI 响应性；验收以界面持续响应、阶段真实和安全取消为准，不设置虚假速度目标。

### D-034：峰值空间预检与历史库存储位置

状态：已确认，并补充用户自定义存储位置要求。

结论：每次写入前由程序按磁盘分别计算并预留最坏路径所需空间，不提供“空间不足仍继续”。Trae Sync 自有的大容量历史数据允许用户选择一个统一存储根目录，默认值可直接使用，无需首次配置。

峰值空间规则：

- 分别计算目标 TRAE 所在卷与 Trae Sync 历史库所在卷；两者位于同一卷时合并计算，不能重复使用同一份可用空间。
- 历史库卷预算至少包含原始证据快照、逻辑恢复副本、目录库临时增长、失败后证据预留和复制过程临时文件。
- 目标卷预算至少包含最坏 WAL 增长、同卷恢复 staging、替换过程临时文件和恢复安全余量。
- 安全余量使用程序固定的保守公式，不向用户暴露调参；初始基线为计算量的 20%，且不低于 512 MiB，最终由 Gate L 的真实峰值数据校准但不能低于实测最坏值。
- 首次预估在请求用户关闭 TRAE 前执行；TRAE 停止且文件稳定后重新读取实际大小并精确复核。
- `target_writing` 前再次检查可用空间，并在目标卷建立已实际分配的恢复空间预留；预留与操作 ID 绑定，只在操作达到已验证安全终态后释放。
- 任何预检、空间预留或写入失败都不能通过自动删除历史、快照或备份解决。
- 可用空间被其他程序突然消耗时，写事务必须回滚或进入 D-025 受控恢复，不能把预检当作唯一保护。

空间不足的用户体验：

- 普通界面只显示涉及磁盘的“需要空间”“当前可用空间”和单一推荐操作，不展示内部估算公式。
- 在任何目标写入前停止；不提供“忽略并继续”按钮。
- 历史库卷不足时主要操作为“更改历史库存储位置”；目标卷不足时提示用户释放该卷空间后重试。
- 已创建的完整备份不因后续空间不足而自动删除；不完整临时文件由 manifest 标记，清理前必须证明其不具备恢复或证据价值。

自定义存储位置规则：

- 默认历史库存储根目录由程序选定，首次使用不要求用户配置。
- 用户可在“存储管理”中选择另一个受支持的本地文件夹；规范化目录库、原始快照、写前备份、失败后证据和已完成操作归档统一存放，避免多个路径配置项。
- 小型启动配置、DPAPI 密钥包装、进行中操作的完整权威 manifest 和最小逻辑断言保留在 Windows 用户本地应用数据目录，确保自定义历史盘暂时不可用时仍能识别并冻结未完成操作；对话正文和大型证据不复制到固定本地目录。
- TRAE 原始数据库位置由所选数据位置决定，Trae Sync 不替用户移动它。
- 为保证替换恢复语义，目标恢复 staging 始终位于 TRAE 数据库同卷，不接受用户重定向。
- V1 支持本机固定磁盘上的普通文件夹；网络共享、云同步目录和可能随时断开的介质在完成专门 Gate 前不作为活动目录库位置。

历史库迁移规则：

- 迁移前禁止存在进行中的扫描、同步、恢复或删除操作，并预检新旧卷峰值空间。
- 先把全部数据复制到新位置，逐文件校验哈希，并用新位置的目录库执行只读打开和完整性检查。
- 验证完成后通过持久化迁移 manifest 切换存储根指针；崩溃后必须能确定旧位置或新位置中哪一个是当前权威副本。
- 切换成功后旧位置保持不变并显示为“可删除的旧副本”；只有用户查看影响并明确确认后才删除。
- 新位置不可用、校验失败或迁移中断时继续使用旧位置，不留下两个都被认为可写的目录库。

Gate L 必须测量正常同步、验证失败恢复、历史库迁移和磁盘并发消耗的真实峰值，并覆盖不同卷、同一卷、预留失败、迁移中崩溃和新位置掉线，验证不会写入空间不足或身份不明的位置。

### D-035：V1 采用“历史跟随当前账号”

状态：已确认，双账号同时保留留待后续版本。

结论：V1 采用“历史跟随当前账号”，不创建双账号独立副本。无冲突项目使用已通过 UI 验证的项目归属转移；目标账号已有同一项目时，使用 D-037 已确认纳入 V1 的会话级重挂，并在发布前通过 Gate M。

规则：

- Sync Executor 对活动数据库中选定且无项目级冲突的项目更新 `project.user_id = current_user_id`。
- 对目标账号已经存在的同一逻辑项目，执行器可以保持所有会话内容 ID 不变，把选中的活动会话重挂到目标项目；正式开放前必须通过 Gate M。
- 会话、消息、turn、task、history、snapshot、FTS 和正文 JSON 不复制、不换 ID、不重写。
- 一个项目在活动数据库中只有一个当前归属账号；V1 不使用“复制到两个账号”“双端同步”或“两个账号各保留一份”等承诺。
- 目标账号原有项目不删除；无冲突的转入项目在目标账号侧形成可见并入。
- 来源账号失去的是项目的当前可见归属，不是底层内容；中立历史库继续保存首次发现来源、历次归属、不可变快照和写前备份。
- 用户以后切换到另一个账号并再次执行“全部历史跟随当前账号”，这些活动项目可以整体跟随新的当前账号。
- 已不在活动数据库中的“仅归档”项目仍不能在 V1 写回或跟随，保持 D-017 边界。

用户体验规则：

- 工作台主操作使用更简洁的“应用到当前账号”，确认页仍明确其底层语义是让项目历史跟随当前账号；产品名称继续使用 Trae Sync。
- 预览按项目显示“账号 A -> 当前账号 B”，并明确目标原历史保留、来源账号将不再显示该项目。
- 完成页使用“已跟随”“已在当前账号”“已排除”“需要处理”，不使用可能暗示物理复制的成功文案。
- 普通用户无需配置该行为；真正的项目图克隆只能作为 V2 独立能力，在完成全部 ID、关系、嵌入引用、FTS 和 TRAE UI Gate 后开放。

### D-036：“历史库 + 同步范围 + 当前 TRAE”简化模型

状态：已确认；D-037 将自定义范围扩展到账号、项目和单条完整对话。

结论：用三层用户心智替代直接围绕数据库来源和迁移规则组织工作台。内部安全机制保持完整，但普通用户只需要查找历史、选择同步范围和应用到当前账号。

```text
历史库       所有已扫描记录、来源和版本
同步范围     希望在账号切换后继续看到的活动项目集合
当前 TRAE    当前平台、数据位置和登录账号
```

历史库规则：

- 用户点击“查找历史”后，工具先建立不可变快照，再把可解析内容收入中立历史库。
- 默认按“来源账号 -> 项目 -> 对话标题”展示；对话标题下包含该 `chat_session` 的全部消息和相关内容。
- 不同账号观察到的逻辑项目和会话可以在历史库中统一分组，但所有来源、快照和版本继续独立保留。
- “当前版本”只是目录库中指向某个 `session_version` 的投影指针；它不删除其他版本，也不是一个可直接替换 TRAE 的新数据库文件。
- 完全相同版本自动去重，严格扩展自动成为当前版本，分叉版本等待用户选择；规则继续使用 D-031。

同步范围规则：

- 使用分段选择 `[全部历史 | 自定义]`，不建立“记录标准”设置页。
- “全部历史”是动态范围：新发现且可同步的活动项目自动纳入，但每次应用前仍展示变化预览。
- “自定义”允许按来源账号、项目或单条完整对话选择；新发现内容进入待处理，不自动加入。
- 单条对话指一个任务标题对应的完整 `chat_session` 及其全部关联内容，不是某一条消息。
- 账号选择批量选择其下项目和对话，项目选择批量选择其下对话；同一稳定 `session_id` 在计划中最多计算一次。

应用规则：

- 点击“应用到当前账号”后先重新扫描活动数据库和当前账号，发现的新历史先安全收入历史库。
- 目标账号没有同一项目时，执行器仍可通过更新 `project.user_id` 让整个项目跟随当前账号。
- 目标账号已有同一逻辑项目时，执行器把同步范围内选中的活动 `chat_session` 重挂到目标项目；单条选择入口只在“自定义”范围中显示。
- 自定义范围只选中项目内部分会话，而目标账号尚无同一逻辑项目时，V1 不能通过项目归属移动完成该范围，也不静默扩大为整个项目。Planner 将其排除并提示用户选择整个项目；创建新的目标项目记录属于后续独立能力。
- 历史库中的旧版本、分叉版本和仅归档内容不写回 TRAE；选择当前版本只影响历史库浏览。
- 如果活动数据库或账号证据相对预览发生变化，旧计划失效并重新生成。
- 应用不会把 TRAE 数据库替换成历史库镜像，也不会删除同步范围以外的记录。

简化工作台：

```text
当前 TRAE：平台 / 数据位置 / 当前账号
历史库：账号数 / 项目数 / 对话数                 [查找新历史]
同步范围：[全部历史 | 自定义]                    [编辑范围]
变化摘要：将跟随 / 已在当前账号 / 需要处理
                                             [应用到当前账号]
```

发现新历史时，普通界面显示新增项目和对话数量；全部模式自动纳入，自定义模式等待选择，不询问覆盖或删除。

### D-037：活动数据库支持会话级重挂与同项目历史并集

状态：已确认纳入 V1；技术可行性已由明文与 SQLCipher 加密副本验证，真实 TRAE UI 继续对话 Gate M 尚未完成。

事实结论：

- 单个任务标题对应一个完整 `chat_session`，可以作为独立执行单位。
- 不需要克隆消息图或重写 ID；只需重挂 `chat_session.project_id`、`session_project.project_id` 以及按会话归属的项目引用。
- 两个账号已有同一逻辑项目时，可以选择目标项目行，把双方不同 `session_id` 的会话形成并集。

### D-038：同项目自动生成会话并入计划

状态：已确认。

结论：在“全部历史”范围中，如果 Work CN Adapter 能可靠确认来源和目标记录属于同一逻辑项目，Planner 自动把来源项目中不同的活动 `session_id` 加入目标项目的会话并入计划，不额外弹出逐项目确认框。

自动化边界：

- “自动”只表示生成计划和预览，绝不表示后台自动写数据库。
- 用户仍需在总预览中看到目标项目、将加入的对话数量、已存在数量和排除数量，并点击一次“应用到当前账号”。
- 目标项目原有对话保持不变；不同 `session_id` 的来源对话全部保留。
- 同一稳定 `session_id` 已在目标关系中时归类为“已存在”，不重复计划。
- 自定义范围只并入用户选中的账号、项目或对话，不因项目匹配而扩大范围。
- 单条会话重挂要求目标账号已有可靠匹配的逻辑项目。目标项目不存在且自定义范围未覆盖整个来源项目时，本次排除；V1 不自动创建项目行或复制 sandbox 配置。

可靠身份要求：

- 不使用项目名称作为身份依据。
- 不把“规范化路径相同”单独视为同一项目；真实样本已出现 `virtual` 与 `unsaved_multi_root` 共用路径。
- Adapter 必须综合稳定 ID、`biz_project_id`、规范化路径、`workspace_status`、`work_mode`、remote、fallback 和多根工作区关系。
- 任一关键证据矛盾或缺失时显示“暂时无法确认是否为同一项目”，排除该项目并继续其余计划。
- V1 不提供绕过身份判定的“强制并入”入口。

普通预览文案：

```text
项目 A：将加入 6 条对话，1 条已存在
项目 B：暂时无法确认是否为同一项目，本次不处理
其他 12 个项目：将跟随当前账号
```

Gate F 除项目身份 fixture 外，还必须验证身份可靠项目自动生成的会话集合准确、重复计划为零、自定义范围不会被扩大。Gate M 验证并入后的列表、搜索、正文和继续发送消息。

```text
backing_up                    正在建立写前备份
backup_verified               写前备份已独立验证
target_writing                目标事务已开始，是否提交可能未知
target_committed_unverified   事务已返回提交，尚未独立验证
target_verifying              正在用新连接验证目标
catalog_reconciling           目标已验证，正在协调历史目录库

verification_inconclusive     因锁定、权限或临时 I/O 无法得出验证结论
failure_preserving            正在保存失败后现场
failure_snapshot_verified     失败后证据已保存并校验
restore_staging               正在目标同卷生成恢复 staging
restore_staged                staging 已独立验证
restore_replacing             正在替换目标文件
restored_verifying            正在独立验证恢复结果

completed                     终态：同步已提交并验证
cancelled_before_write        终态：用户在目标写入前取消
failed_safe                   终态：写前失败且已证明目标未改变
not_applied                   终态：崩溃协调证明事务未提交或已回滚
restored_verified             终态：同步异常，已恢复写前状态并验证
manual_recovery_required      终态：证据不足或自动恢复条件不成立
```

崩溃后判定顺序：

1. 保持 TRAE 停止，读取权威 manifest、目标三件套身份和备份证据。
2. 以只读新连接打开目标，检查 schema、计划涉及的项目/会话归属、数量、稳定 ID 和关系断言。
3. 逻辑状态匹配写前断言时，结束为 `not_applied`，不执行恢复，也不重放事务。
4. 逻辑状态匹配预期写后断言且完整性检查通过时，继续目录库协调并结束为 `completed`。
5. 能明确证明已提交但完整性检查失败时，按 D-025 保存现场并进入受控自动恢复。
6. 不能匹配任何已知逻辑状态、账号或数据位置证据变化、数据库无法可靠打开时，进入 `manual_recovery_required`。

证据规则：

- 物理证据包括文件身份、存在性、大小、哈希、WAL/SHM 状态和读取时间，用于证明备份、识别外部变化和保护现场。
- 逻辑证据包括 schema 版本、计划目标账号、项目/会话归属、行数、稳定 ID、唯一约束和关系断言，用于判断事务是否提交。
- SQLite checkpoint 或崩溃恢复可能改变 DB/WAL 的字节布局；禁止只比较整文件哈希来判定写事务是否提交。
- `backing_up`、`target_writing`、`failure_preserving`、`restore_staging`、`restore_replacing` 等意图状态先完整落盘，再开始对应副作用；`backup_verified`、`target_committed_unverified`、`failure_snapshot_verified`、`restore_staged` 等结果状态在副作用返回后落盘。若在两次落盘之间崩溃，重启后从上一个意图状态和实际证据协调，不盲目重复阶段。

自动恢复仅在 D-025 的备份、失败现场、同卷 staging、目标未漂移和恢复后验证条件全部满足时执行。任何条件不成立都进入 `manual_recovery_required`，不继续覆盖，不启动 TRAE，不删除任何证据。

普通界面只显示“正在备份”“正在应用”“正在验证”“正在恢复”“恢复完成”或“需要恢复”；内部状态、哈希和断言只在详情与诊断报告中显示。

Gate C 必须对每个非终态注入进程终止、断电等价中断和重启协调，并证明不会重复应用、误判成功、覆盖外部新状态或丢失写前/失败后证据。

### D-040：计划证据绑定、账号漂移与跨进程排他

状态：已确认。

结论：同步计划必须绑定生成预览时的账号、数据位置和数据库证据。应用时任一证据变化都会使旧计划失效，系统返回刷新后的预览，绝不把原计划静默改投到另一个账号。同一数据位置跨进程同时只允许一个有副作用的操作。

计划必须持久化：

```text
operation_id
data_location_id
current_user_id
账号证据指纹及读取时间
database.db / WAL / SHM 物理证据
schema、项目/会话归属和稳定 ID 等逻辑指纹
同步范围及预期写后断言
```

账号证据只保存不可逆指纹和非敏感身份字段，不保存 Token 或可还原的认证正文。

执行顺序：

1. 用户可以长时间查看预览，预览阶段不依赖持有排他锁维持有效性。
2. 点击“应用到当前账号”后，按固定顺序获取目录库单写锁和目标 `data_location_id` 跨进程排他锁。
3. 协调该数据位置所有未完成 manifest；存在未解决操作时不开始新操作。
4. 重新读取当前账号、账号证据、目标文件身份和数据库逻辑指纹。
5. 任一证据与计划不同，释放锁并返回新预览；不创建写前备份，不写目标。
6. 证据一致时建立并验证写前备份，然后进入不可取消的目标写阶段。
7. 在事务提交前再次读取账号证据；发生漂移时回滚事务并结束为 `not_applied`。
8. 提交后再次读取账号证据；此时才发现外部漂移时不启动 TRAE、不把已确认的目标账号改成新账号，进入协调页面并重新生成后续计划。
9. 锁保持到目标验证、目录库协调和 manifest 进入终态后才释放。

跨进程规则：

- 使用操作系统级、可检测持有进程退出的锁，不依赖普通内存变量。
- 所有进程按“目录库单写锁 -> 数据位置锁”的固定顺序获取，避免死锁。
- 同一数据位置的扫描、快照、同步、恢复、存储迁移和删除互斥。
- 第二个实例仍可浏览已提交的历史库快照，但修改入口显示“另一项操作正在进行”。
- 进程异常退出会释放操作系统锁，但新进程必须先按 D-039 协调未完成 manifest，不能仅因锁已释放就开始新写入。

普通用户不配置锁、指纹或重试策略。证据漂移时界面只说明“当前账号或数据已变化，已为你刷新预览”，并重新显示实际目标账号和变化摘要。

Gate B 事实调查已验证账号证据来源，生产解析器仍需实现测试；Gate C 验证崩溃后锁释放与 manifest 协调；Gate G 使用两个真实进程和账号管理器并发切换，验证不存在交错写、静默改投或旧计划继续执行。

### D-041：DB/WAL/SHM 存在性、备份与恢复

状态：已确认。

结论：`database.db` 是必需文件；`database.db-wal` 和 `database.db-shm` 是按捕获时实际状态记录的可选文件。可选文件原本不存在属于正常状态，不能被误报为备份失败。恢复发布经过验证的逻辑数据库时，禁止复用失败状态留下的 WAL/SHM。

备份 manifest 对每个文件分别记录：

```text
relative_name
present_at_capture
size_if_present
sha256_if_present
file_identity_if_available
captured_at
```

捕获规则：

- `database.db` 不存在时立即停止，不创建空文件，也不进入任何目标写入阶段。
- WAL/SHM 存在时必须与 DB 一起复制并逐文件校验；复制或校验失败则停止。
- WAL/SHM 不存在时在 manifest 中明确记录 `present_at_capture = false`，不创建占位文件。
- 文件存在性在捕获前后发生变化表示来源仍在活动或发生外部漂移，本次快照无效，返回重新检测。
- 原始证据快照保留捕获时的精确存在性；逻辑恢复副本通过 SQLCipher/SQLite Backup API 获得一致的已提交状态。

逻辑恢复规则：

1. 保持 TRAE 停止并关闭 Trae Sync 的全部目标数据库连接。
2. 先把恢复前目标目录中的 DB/WAL/SHM 按实际存在性保存为失败现场证据并验证哈希。
3. 在目标同卷 staging 生成并独立验证单文件逻辑数据库。
4. 把目标目录中旧 DB/WAL/SHM 移入本次证据隔离区；不直接删除，也不把旧 WAL/SHM 留在目标数据库旁。
5. 原子发布已验证的 `database.db`；目标旁不发布旧 SHM，WAL 只在所选恢复格式明确需要且已经作为一致集合验证时发布。
6. 使用新连接打开目标，让 SQLite 按需要重新创建 WAL/SHM，并执行身份、schema、逻辑断言及两层完整性检查。
7. 全部验证通过后才进入 `restored_verified`；失败时保留 staging、恢复前现场和写前备份，进入 D-039 协调。

普通用户不配置三件套策略。界面只显示备份、验证和恢复阶段；文件存在性及哈希放在详情中。旧 WAL/SHM 作为证据保留，只有用户在备份管理中明确删除对应证据集时才删除。

Gate C 必须覆盖 WAL/SHM 同时存在、仅 WAL 存在、两者均不存在、捕获中出现/消失、未 checkpoint WAL、恢复目录残留旧 WAL 和恢复中断等 fixture。

### D-042：Trae Sync 目录库旁路升级

状态：已确认当前基线；具体跨版本兼容和迁移内容随实际版本更新再讨论。

结论：Trae Sync 自身的 SQLCipher 历史目录库不做原地升级。应用先保持当前库不变并只读，在同级 staging 副本上执行 schema 和内容映射迁移；只有新副本完成独立验证后，才原子切换当前库指针。

升级流程：

1. 获取目录库单写锁，协调所有未完成操作，禁止扫描、同步、恢复、迁移和删除。
2. 记录当前目录库文件身份、schema 版本、Adapter 映射版本、密钥包装版本和当前指针。
3. 保持旧目录库不变并切为只读，复制到同级 staging；不同卷存储迁移不与版本升级合并执行。
4. 在 staging 内通过版本化迁移逐级升级，不跳过中间迁移。
5. 使用新连接验证 SQLCipher 密钥、目标 schema、`cipher_integrity_check`、`integrity_check`、账号/项目/会话数量、来源映射、用户标签、版本选择、操作记录和备份引用。
6. 验证通过后先落盘升级 manifest，再原子切换小型当前库指针。
7. 切换后重新打开当前指针指向的库并复核；通过后才允许新的目录库写入。
8. 旧目录库标记为受保护回滚副本，绝不自动删除；只有用户在备份管理中明确解除保护并删除。

失败规则：

- staging 复制、迁移或验证失败时不切换指针，旧库字节和当前指针保持不变。
- 新版本应用至少能以兼容只读模式打开上一受支持版本的目录库；迁移失败时仍允许浏览已有历史和导出诊断，但禁止任何会修改 TRAE 或目录库的操作。
- 遇到未知 schema、Adapter 映射或密钥包装版本时停止升级，不猜测转换。
- 权威操作 manifest 不依赖尚未升级成功的新目录库，应用升级不能阻断未完成 TRAE 操作的恢复判断。

普通用户不配置 schema、迁移步数或兼容策略。界面只显示“正在升级历史库”“升级完成”或“升级未完成，已保留原历史库”。具体迁移支持范围和旧版本保留要求在每次真实版本更新时重新评审。

目录库升级 Gate 必须覆盖复制中断、每个迁移步骤崩溃、验证失败、指针切换前后崩溃、旧盘空间不足和回滚副本只读打开。

### D-043：可移动历史库与固定恢复权威信息

状态：已确认。

结论：用户可把大型历史库迁移到受支持的本地磁盘；进行中操作的完整权威 manifest 和最小恢复断言固定保存在 `%LOCALAPPDATA%\Trae Sync\recovery`。自定义历史盘不可用时，应用仍能识别危险状态并冻结目标，但不能开始恢复、新扫描或任何写操作。

固定本地恢复区只保存：

```text
活动 operation_id 与唯一状态
data_location_id 和目标文件身份
当前账号不可逆证据指纹
写前与预期写后的最小逻辑断言
外部备份、失败证据和 staging 的路径、存储根 ID 与哈希引用
目录库当前指针和迁移状态
manifest 格式版本及校验信息
```

固定恢复区不保存对话正文、消息索引、原始数据库快照或大型备份。大型内容统一位于用户选择的历史库存储根：

```text
SQLCipher 规范化目录库
不可变来源快照
写前逻辑恢复副本
失败后证据
已完成操作归档和诊断附件
```

存储根身份规则：

- 每个历史库存储根创建稳定随机 `storage_root_id`，固定本地配置绑定该 ID、规范化路径和目录库身份。
- 路径存在但 `storage_root_id` 不匹配时视为另一存储根，不自动采用。
- 配置的存储根不可用时，禁止在默认位置或原路径创建空历史库，避免产生两个权威副本。
- 存储根重新可用后，先验证 ID、目录库指针、引用文件身份和哈希，再解除冻结。
- 本地 manifest 足以判断并冻结未完成操作；引用的备份不可访问时不能开始自动恢复。

存储迁移规则继续使用 D-034：复制和验证新根后原子切换指针，旧根保持只读并显示为可删除旧副本，只有用户明确操作才删除。进行中操作存在时禁止迁移，版本升级与存储迁移不得合并为同一次操作。

普通用户只选择一个“历史库存储位置”，不配置 manifest 或恢复目录。固定恢复区占用很小并由程序管理，不提供迁移选项；诊断页可显示其状态，但不暴露配置压力。

Gate L 必须覆盖自定义盘启动前缺失、操作中掉线、恢复时掉线、同路径换盘、`storage_root_id` 不匹配、重新连接、跨卷迁移中断和旧根保留，证明不会误建新库、发生双写或遗忘未完成操作。

### D-044：账号检测失败时的写入权限

状态：已确认。

结论：手工选择账号不能替代当前登录账号证据，也不能解锁任何 TRAE 数据库写入。它只用于浏览、标注和整理 Trae Sync 历史库中的已见账号。

固定规则：

- 账号证据有效且一致时，才生成可执行同步计划。
- 账号证据缺失、过期、未知或冲突时，当前数据位置进入只读状态；仍可浏览已有历史和诊断证据。
- 用户需要启动 TRAE 完成登录，让 Adapter 取得权威日志账号并绑定当前认证指纹；随后关闭 TRAE，且指纹保持不变，才允许继续同步。
- 用户在界面中点击某个已见账号，不改变证据状态，不把计划目标改成该账号。
- `project.user_id`、`state.vscdb` 历史账号键和第三方账号管理器状态都不能作为人工覆盖依据。
- 重新检测仍失败时停止，不提供“我已确认，仍然继续”入口。

普通界面只显示“无法确认当前账号”和“重新检测”。详情页说明需要启动 TRAE 完成登录后再关闭；不向用户暴露密文、指纹算法或日志解析规则。

此规则比错误账号写入多一次启动和关闭操作，但满足“宁可保守停止，也不把历史写到错误账号”的数据保护要求。
