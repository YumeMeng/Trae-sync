## 项目核心需求（用户定义，最高优先级）

1. **账号保存**：登录 token 与 refresh token 持久化存储，随时可用。
2. **对话记录同步**：消除不同账号间对话记录隔离——所有账号共用一套规定的历史对话记录。
3. **签到功能**：每账号绑定持久设备身份，HTTP 直连完成签到（综合 2026-08-20/21 全部实验结论）。
4. **账号切换**：仿对标工具的自有切换方式，账号集中排列、显示基础信息与剩余积分。

以上为项目存在的理由。规范、架构、计划均服务于这四条；与四需求冲突的既有约束按本记录解除。

## 决策详录

### D1 架构策略：现有结构上收敛

保留资产（已验证可用）：
- crate 分层（domain / application / infrastructure / ports）与组合根
- 签到 HTTP 协议层（端点、头、业务码分离——`checkin_http.rs`，45 单测通过）
- OAuth 登录流程（PKCE + 本地回调 + ExchangeToken）
- DPAPI 凭据加密存储、EC P-256 设备密钥对
- SQLCipher 历史库读写资产（raw key 分类与导出契约已并入 `docs/TECHNICAL_BASELINE.md`）
- 桌面 UI 四页骨架（Overview/History/Accounts/Settings，46 E2E 通过）

废止/改造：
- Gate 证据体系（`evidence/gates/`、GATE_PLAN.md 流程）——对真实数据的卡点全部移除，已产出证据归档不再维护
- tickets T01-T21 计划体系——按 Phase 0-4 重排（见新 tickets.md）
- 强制备份/验证/协调流程——见 D2

### D2 数据红线解除

旧红线（AGENTS.md）："不写真实活动数据库""强制双备份、完整验证、崩溃协调、用户确认"。
新约定：
- 允许直接读写 TRAE 真实数据（SQLite 库、API）
- 数据安全保障 = App 内**手动备份入口**（用户自选备份位置、内容、时机）+ 破坏性批量操作（删除/覆盖/迁移）执行前单次确认
- 保留铁律：**工具不得自动删除用户历史、快照、备份或失败证据**（此条与红线无关，永久有效）
- 工程常规（原子写、写后校验、测试覆盖）继续作为工程纪律，但不再作为流程门禁

### D3/D4 主库方案（需求 2 落地路径）

用户构想（原文要点）：项目有"主库"；有分类区显示各账号对话记录；可把某条对话收入主库；可把主库对话返还到原账号或自定义账号；主库模式可开关——开启时所有账号打开后看到并操作主库，关闭后恢复各自独立历史。

修正过的两个语义（已向用户指出并接受）：
1. 主库开启期间产生的新对话归主库；关闭后账号独立历史中**没有**它们，需手动"返还"——不是自动的。
2. 主库模式下同时只允许一个 TRAE 实例（SQLite 单写者约束）。

机制对比（曾评估的三方案）：
- 方式一 目录级切换：主库 = 专用 data_dir；开启时注入当前账号凭据后以主库目录启动 TRAE。TRAE 内完整共用体验。**已选，分阶段。**
- 方式二 会话级双向同步：无感但合并语义复杂（删除/冲突传播、ID 重写、附件引用），V1 风险大。未选。
- 方式三 App 内主库：App 只读阅览全部账号历史 + 手动搬运会话。安全但不满足"TRAE 内共用一套历史"。作为方式一第一阶段能力与退路。

两个已识别技术风险（待 Phase 4 实测，不阻塞前期阶段）：
- 凭据注入互换（A 注入后换 B）TRAE 是否无感接受
- ~~云端历史同步冲突~~——用户已明确：纯本地，云端不考虑

### D5 签到虚拟设备策略（需求 3）

设计：每账号首次 OAuth 登录时生成随机 16 位设备 ID（首位 1-9）+ EC P-256 密钥对 + **随机 MachineID**（切断与物理机关联，零成本加固），随 ExchangeToken 注册，与 token/refresh token 同入 DPAPI 凭据包永久绑定。签到、续期永远用同一设备身份。

未决风险（Phase 0 实验）：虚拟设备首次 claim 是否被 9074（陌生设备门禁）拦截，取决于服务端设备信任是"注册即建档"还是"签到成功才建档"。LY（有签到史，最严苛对象）实测定胜负：通过 → 设计成立；9074 → 回设计台。

实验依据（全部来自 `.scratch/checkin-http/` 实测，详见 TECHNICAL_BASELINE 与复现手册）：
- 9074 = 设备 ID 无成功签到记录（2026-08-22 P0-y 终裁：有发放史的编造 ID 跨账号跨产品畅通；注册记录仅为获得史的途径之一，非必要条件。详见 ADR-0019 v3）
- 9095 = 设备日配额（"当前设备今日已经签到"）；2026-08-22 P0-x 实测：真实设备当日第 3 账号 claim 被拒，配额 = 2 账号/设备/天
- 1001 = status 查询业务码：服务端拒绝该 token（2026-08-22 审计发现，导入凭据被服务端侧作废场景；token 未过期但被拒，OAuth 重新授权可解）
- claim 幂等性：当日已签后重复 claim 返回 code=0 但不发放——**判定真发放必须看 checked_in 翻转**
- 无账号级冷却（B 距上次成功 4.3h 即再发放）；无 IP 配额（同 IP 同日多次成功）

### D6 账号来源：仅 OAuth

Manager 的 accounts.json 导入路径**不做**（用户明确：Manager 只是参考工具，不应成为挂带产品）。现有 A/LY/梦梦等账号在 App 内重新 OAuth 授权一次。凭据结构因此完全统一（access + refresh + 设备密钥对）。

### D7 实例模型：默认单开 + 可多开

- 账号列表点账号 = 关当前实例、启动该账号实例（单窗口快速切换）
- 另设"多开"按钮可例外并行
- 主库模式开启时强制单实例
- 风控结论支撑此决策（见下）

**风控分析结论（Q7 讨论固化）**：
- 服务端设备身份由硬件指纹派生，data_dir 隔离从未隐藏机器身份——本机全部 TRAE 应用设备哈希收敛为同一值已实证（`EE5A02EE69AAA646`）；"同一环境"是数月来的一贯事实，四账号无任何账号级风控迹象
- 实测到的"风控"只有签到端点两道配额闸门（9074/9095），是限流不是惩罚
- 虚拟设备方案在签到层比 Manager 隔离更有效（Manager 各实例在服务端共享同一设备 ID，配额挤一个坑；虚拟设备天然分摊）
- data_dir 的真正价值 = 本地状态隔离（登录态/缓存互不踩踏），保留
- 残余不可控风险 = 同 IP；目前无按 IP 打击迹象，代理支持留作后路，现在不做

### D8 签到触发：打开时检测 + 自动签

- App 打开时自动查各账号今日签到状态；设置项"打开时自动签到"默认开启
- 手动"全部签到"按钮随时可用（串行逐账号 status→claim→status，实时进度）
- Token 续期检查也在打开时做（App 是 TRAE 启动入口 → 只要使用 TRAE 就会开 App → Token 永活）
- 托盘常驻/系统计划任务不做，留作后续可选增强
